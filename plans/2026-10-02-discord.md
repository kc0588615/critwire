# Mission: critwire Discord

This file is the mission's state. Agents: follow "In a mission session" in `~/.claude/CLAUDE.md`, and keep this file current.

## Brief


### Goal

Players can send feedback from the studio's Discord server, and the server hears back when things change. All of it works through Discord's HTTP interactions, so there's no always-on bot process. When this mission is done:

1. **Feedback from Discord.** A critwire Discord app offers:
   - **`/feedback`:** opens a Discord form (a modal) that asks Bug or Idea, a title and details, plus platform and version for bugs. It creates a **private report in the game's review queue**, through the same content filter and the game's "review before public" setting (on by default). The player gets a private confirmation with a link to the board.
   - **"Send to critwire" on a message** (right-click → Apps): turns a player's Discord message into a report, credited to its author. Only members with Manage Messages can use it, so players can't import other people's messages.
   - **What a report records:** the Discord username and user ID, privately, so the studio can follow up. They're never shown publicly.
   - **Rate limits:** per Discord user, per game.
   - **Security:** every request's Ed25519 signature is verified, and old requests are rejected using the timestamp.
   - **No voting from Discord.** A Discord identity would be a second vote for the same person, which the owner rejected (2026-10-02).
2. **Posts to Discord.** Critwire posts to a channel the studio chooses when an update is published, and when a feedback item's **public stage** changes to Planned, In progress or Shipped.
   - Send one post per public stage change. Several changes in quick succession become one post.
   - Never post for flagged content, held games or suspended studios. The job loads data with `overrideAccess: true`, so it must check this itself.
   - Each post links to the item or the update on the portal.
3. **One setup.** The "Put critwire on your site" panel (from the `reach` mission) gets a **Discord** tab:
   - "Add critwire to your Discord" installs the app on the studio's server and links the server to the studio.
   - The studio picks the channel for posts. A webhook or the installed app may do the posting; the architect picks whichever needs fewer steps from the studio.
   - When a studio has several games, `/feedback` lets the player choose the game.
4. **Self-hosting.** The Discord features are off unless their environment variables are set. `docs/discord.md` explains, step by step, how a self-hoster creates their own Discord application and connects it.
5. **The hosted instance.** Add a handoff item with click-by-click steps for the owner: create critwire's Discord application in the Discord Developer Portal, copy the IDs and keys it needs, and, once production exists, set its Interactions Endpoint URL. This doesn't block the mission.

### Why

Indie studios' players talk on Discord. The tools indies adopt for feedback are Discord-first, and players won't go looking for a portal. The owner asked for feedback to be collected from Discord (2026-10-02). Posting status changes back closes the loop where the players are.

## Architecture

Architect: Opus 5.5, 2026-10-02. I read the Brief, the integrations review (Must-fix 5), `AGENTS.md`, `docs/{architecture,patterns,features,integrations,share,self-hosting}.md`, the code cited below, and the Payload 3.85.2 and Next 16.2.6 sources where a claim depends on them. ### In short

- **No bot user and no bot token.** A studio adds critwire with one Discord authorization (`applications.commands webhook.incoming`). On Discord's own screen it picks the server and the channel for posts. Commands arrive as signed HTTP interactions, and posts go through the webhook Discord creates in that channel.
- **One link per game** (`GameProject.discord`: server, channel, webhook URL). Only the OAuth callback writes it (super admins can too), and it does so as the signed-in user, so every access rule still applies. The one system write, `stopPosting`, only clears the channel and webhook, and only if the stored webhook is the one that just failed.
- **Discord reports take the web form's path.** That path moves out of the route into one module. The Discord identity goes into private fields on the submission and never reaches the public item.
- **A form submission is saved before Discord gets its answer**, and is bound to the game it was opened for. A unique interaction ID on the report makes a replayed request create nothing.
- **Posts are delayed jobs.** A post waits 60 s and is merged with later changes by Payload's concurrency `supersedes`. When it runs, the job reads its subject as an anonymous visitor, so the existing public-read rules decide what counts as held, suspended or private. A super-admin-only `discord-posts` log keeps it to one post per update and one per stage.
- **Off unless three env vars are set.** E2E points the app's Discord API base at a local stand-in.
- **The baseline flake is a real Next race** (verified in Next's source, F1). This mission fixes the test only. The race stays a known production defect until the owner picks a fix (H15).

### Findings

Ranked by impact on this mission.

**F1. The `patch-notes.spec.ts:265` flake is a real ISR race (verified). Fix the test in this mission and hand the production fix to the owner.**
- **How the race works:**
  - Next stamps an ISR entry's `lastModified` when the entry is *written* (`node_modules/next/dist/server/lib/incremental-cache/file-system-cache.js:251-255`).
  - An entry counts as stale only if one of its tags was revalidated *after* that stamp (`tags-manifest.external.js:44-52`).
  - So a render that read the database before the write committed, but finished after `revalidatePath`, is stored as fresh. It keeps the old data until the 1-hour fallback (`updates/[slug]/page.tsx:14`).
- **Why the test hits it:** the test opens the feed (`patch-notes.spec.ts:282`), whose `<Link>`s (`UpdateEntry.tsx:29`) prefetch both detail pages as soon as the page loads. It unpublishes straight away, so in about 1 run in 5 the prefetch render of the pulled note straddles the write.
- **Fix here (first step, test only):** wait for the pulled note's prefetch to finish before the PATCH, with a comment naming this race. Then rerun with `--repeat-each=10`.
  - Start `page.waitForResponse` for the pulled note's detail pathname *before* opening the feed. Prefetches carry `_rsc` in the query, so match the pathname only. After the feed assertion, await that response and its `finished()`.
  - This is deterministic, unlike `networkidle`, which depends on the prefetch starting within 500 ms of the last request. If Next ever stops prefetching that link, the wait times out and the test fails loudly instead of passing by luck.
  - This isn't suppressing a failure. The test is about unpublishing, and the race needs a render in flight that the test started itself.
  - Keep the wait in this test, not in the spec's shared `open()`: `eventually` loops call `open()`.
- **Production impact:** if a visitor's render is in flight while a studio writes, that page stays stale for up to an hour. The window is narrow, but it's a real defect, and fixing the test doesn't fix it. Changing the cache's safety net reverses the owner's H4 decision, so it's proposed as H15 (§14) rather than changed here, and it's listed under Risks as known and unresolved.

**F2. The submission path lives inside the web route, so Discord would duplicate it (DRY).**
- **What's inline today:** the field rules (`feedback/new/submit/route.ts:28-36`), the refusals (form not native, ideas off) and the `issue-reports` create (`:64-100`).
- **Fix:** move them into `src/lib/game-portal/reports.ts`, reusing `getReportRoute` and `acceptsIdeas` (`formRoutes.ts:70-82`):
  - `reportFieldsSchema`: Zod for title (3–160), description (10–5000), platform and version (≤120 each) and type. The route extends it with category and email.
  - `reportRefusal(project, type)`: a query that returns `null`, `'not-native'` or `'no-ideas'`.
  - `createPlayerReport({ project, fields, discord? })`: a command. It asserts `reportRefusal(...) === null` and throws otherwise, so no caller can skip the check. Then it makes the one `payload.create` (`overrideAccess: true`, `status: 'NEW'`, tenant taken from the project) and returns the doc, as `payload.create` does.
- The web route keeps its guard, its answers and its behaviour; `reports-contact.spec.ts` must stay green.

**F3. Discord webhook support is tied to the contact form (Must-fix 5).**
- `validateContactDiscordWebhookUrl` runs only when `target === 'DISCORD_WEBHOOK'` (`discordWebhook.ts:39-49`).
- The delivery code is inline in the contact task (`jobs/contact.ts:117-169`, fetch at `:137-161`): the allowlist re-check, `redirect: 'error'`, the timeout, and a throw on non-2xx.
- **Fix:**
  - **`validateDiscordWebhookUrl`** always runs. The contact validator calls it after its own target check.
  - **`executeDiscordWebhook(url, body)`** goes in `src/lib/discord/webhook.ts`, used by both the contact task and the new tasks.
    - It always adds `allowed_mentions: { parse: [] }`, so player text can never ping `@everyone`.
    - It throws `DiscordWebhookGoneError` on 401 or 404 (the webhook was deleted).
- **The contact task keeps its behaviour:** a `DiscordWebhookGoneError` fails the job, which retries as today, and never clears `contact.discordWebhookUrl`. Only the post jobs turn it into `stopPosting` (§9).
- `isAllowedDiscordWebhookUrl` (`:17-32`) is reused unchanged.

**F4. Must-fix 5's "run the job right after queueing it" contradicts the Brief's merging of quick changes.**
- The contact route runs its job at once (`contact/submit/route.ts:60-67`). Posts must wait instead, so quick changes become one post; the review's own Risks section suggests a one-minute delay.
- **Payload 3.85 provides both pieces:**
  - `jobs.queue({ waitUntil })`.
  - Task `concurrency: { key, supersedes: true }`, which deletes older pending jobs with the same key (`node_modules/payload/dist/queues/localAPI.js:57-140`, deletion at `:99-140`). It needs `jobs.enableConcurrencyControl: true`, which adds an indexed `concurrencyKey` column, so it needs a migration.
- The existing per-minute autorun (`payload.config.ts:146`) runs them.
- Hooks couldn't use `runByID` anyway: they run inside the write's transaction.

**F5. A job's `req.user` depends on who runs the queue. That's a bug risk for the held and suspended checks.**
- **Who runs the queue:**
  - The autorun and `runByID` use a local request with no user.
  - `GET /api/payload-jobs/run` passes on the caller's request: a super admin's, or the `CRON_SECRET` bearer's (`queues/endpoints/run.js`, `runJobs/index.js:250`, `payload.config.ts:117-124`).
- **Why that matters:** `publicRead` gives any signed-in user `true` (`access/publicRead.ts:32-35`). A job that checked visibility with `overrideAccess: false, req` would therefore post held or suspended content whenever a super admin ran the queue.
- **Rule:** the jobs read their subject **without passing the job's `req` and without a user** (`req.payload.find({ overrideAccess: false, … })`), exactly as the portal's queries do (`lib/game-portal/patchNotes.ts:21-45`).
- The Brief's "the job loads data with `overrideAccess: true`, so it must check this itself" becomes: the visibility check *is* the access rule.
- **The privileged operations are named helpers with `overrideAccess: true`:** the webhook read (`gameWebhook`), the post log's reads and writes, and `stopPosting` (§9). In jobs none of them gets the job's `req`, so the runner's user changes nothing. In hooks they pass `req` only to stay in the write's transaction.

**F6. Post state can't be stored on the patch note.**
- PatchNotes have drafts and versions (`PatchNotes/index.ts:102-105`), and their `afterChange` revalidates every updates page (`revalidatePatchNotes.ts:19-41`).
- A job that wrote a "posted" flag would create a version, could bury a studio's pending draft, and would churn the ISR cache.
- Hence a separate log collection (§10).

**F7. Two existing shapes don't fit Discord: the public-form guard and the share panel.**
- **The guard:** `guardPublicForm` limits by client IP and checks Turnstile (`public-forms/guard.ts:27-51`). Discord's requests come from Discord's servers and can't carry Turnstile. Instead, the Ed25519 signature proves the request is Discord relaying a signed-in Discord account, and the rate limit keys on the Discord user ID (§8).
- **The share panel:** `SharePanel` takes only public `{ siteURL, slug }` (`SharePanel.tsx:9-12,39`), because the welcome panel renders it on the public hub (`WelcomePanel.tsx:35`). The Discord tab needs the game's ID, plus the private link state in the admin only, so it gets an optional `discord` prop (§11).
- **Referral tags:** `REF_SOURCES` already plans for a `discord` source (`share/platforms.ts:7-12`). Add it with the label "Discord", so links in posts and replies show up in "Where players come from".

**F8. The Upstash stand-in can't trigger a limit.**
- `fakeUpstash.ts:69-76` answers every `EVALSHA` with "allowed", so no E2E test can see a rate limit.
- Making it faithful everywhere would break the suite: every spec shares one client IP (`unknown`), and signup allows 5 an hour.
- **Fix:** run the real sliding-window logic (the script in `@upstash/ratelimit` 2.0.8, `dist/index.js:229-272`) only for keys under `ratelimit:discord-`.

**Fine as is, and reused:**
- **The public read rules** (`publicRead.ts:17-26`): unchanged, and they are the post jobs' guard (F5).
- **Submissions stay private:** IssueReports are never public (`IssueReports/index.ts:26-34`), and promotion copies only title, description, type and category (`createIssueFromPublishedReport.ts:64-75`). Private Discord fields can't leak through the item, the JSON feeds or the embed.
- **Content filter and review:** `screenTextHook` and `autoPublishReport` (`autoPublishReport.ts:15-37`) give Discord reports the filter and the review setting with no new code.
- **Hook conventions:** the Issue hooks ignore fields outside their lists (`revalidateIssueLanding.ts:17-27`), so kanban `_order` writes stay quiet. The new hook follows the same rule: only a change of public stage counts. Hook queries pass `req` (embed-mission Decision, "Hook queries run in the write's transaction"), and so will the new ones.

#### 2. Configuration and "off unless set"

**Variables:**
- `DISCORD_APPLICATION_ID`: a snowflake, `^\d{17,20}$`.
- `DISCORD_PUBLIC_KEY`: 64 hex characters.
- `DISCORD_CLIENT_SECRET`.

All three or none. A blank value (after `trim()`) counts as unset, as in the other `checkEnvironment` checks; the E2E self-hosted server sets all three to `''`. A partial or malformed set stops the server at boot, naming the variable (`checkEnvironment`, `instrumentation-node.ts:11-21`).

**`DISCORD_API_BASE_URL` (development and E2E only):**
- The default is `https://discord.com/api/v10`.
- When set, it must be an http(s) loopback origin (`127.0.0.1`, `localhost` or `::1`); anything else stops the server at boot. That way a typo can never send the client secret to another host.
- It isn't used for the browser's authorize URL, which is always `https://discord.com/oauth2/authorize`.

**What "off" means:**
- The three routes answer 404 before reading the request.
- There's no Discord tab.
- The hooks queue nothing; they check the env first, so there's no database read.
- A job already in the queue completes with `{ posted: false }`.
- Command sync is skipped.
- Existing links stay in the database.

No new setting for the post delay or the limits.

#### 3. The Discord application: scopes, commands, registration

**Scopes: `applications.commands webhook.incoming`, no `bot`.**
- **Commands:** they work with `applications.commands` alone, and the member's permissions arrive in each interaction.
- **Posts:** they go through the webhook Discord creates when the studio picks a channel on the authorization screen.
- **What the studio needs:** Manage Server and Manage Webhooks, which Discord enforces on that screen.
- **Fewer steps for the studio:** one authorization covers install, server and channel. A bot would need a bot token, its own channel permissions, and a channel picker in critwire built on the bot API.

**Commands** (global, guild only: `contexts: [0]`, `integration_types: [0]`):
- `/feedback` (CHAT_INPUT, type 1):
  - One required STRING option, `type`, with choices Bug `bug` and Idea `idea`.
  - No `default_member_permissions`, so everyone can use it.
  - Bug or Idea is a command option rather than a field in the form, so the form can ask for platform and version on bugs only and still fit the game picker within Discord's 5-field limit. Discord shows the two choices as soon as the player types `/feedback`. Recorded under Decisions as a deviation from the Brief's wording.
- `Send to critwire` (MESSAGE, type 3): `default_member_permissions: "8192"` (Manage Messages), so Discord hides it from other members by default.

**Registration: `syncDiscordCommands()` at boot.**
- It's called from `register()` after `checkEnvironment()`, in the Node runtime only and never during `next build` (`NEXT_PHASE`). It's fire-and-forget, so it never blocks or fails the boot.
- It gets a client-credentials token: `POST /oauth2/token` with `grant_type=client_credentials`, `scope=applications.commands.update` and Basic auth.
- Then it overwrites the commands with `PUT /applications/{id}/commands`, which is idempotent.
- Success logs one info line.
- **Retries without a restart:** a network error, a 429 or a 5xx retries in the same process after 1, 5 and 30 minutes (unref'd timers), logging each failure; the last one goes to Sentry. Any other 4xx (a wrong secret, a rejected definition) goes to Sentry at once and stops, since waiting can't fix it. The next boot starts over.
- **Why at boot:** the Docker image has no `tsx` and no scripts, and this way the definitions always match the deployed code with no operator step.

#### 4. Linking a game to a server

**Storage: a `discord` group on GameProject** (label "Discord"):
- **Fields:**
  - `guildId`: text, indexed.
  - `channelId`: text.
  - `webhookUrl`: text, validated by `validateDiscordWebhookUrl`.
- **Read access:** `tenantMemberFieldRead` on the group, like `contact.discordWebhookUrl` (`GameProjects/index.ts:209-221`).
- **Create and update access:** `discordLinkFieldAccess`, which allows a super admin, or a write whose `req.context.discordLink === true`.
  - `req.context` is set only by server code through the Local API's `context`, never by REST or GraphQL clients. So a studio can't forge a server ID through the API.
  - The callback still writes as the signed-in user with `overrideAccess: false`, so collection access, the plugin's tenant scope and `enforceTenantWrite` (membership, suspension) all apply.
- **The one system write** is `stopPosting` (§9), which only clears a link whose webhook just failed.
- **Admin:** read-only in the sidebar, shown only while linked, with the description "Managed from the Share tab".

**Install: `GET /api/discord/install?game=<id>`**, a plain link from the tab.
1. 404 when off.
2. No session (`payload.auth({ headers })`) → 303 to `/admin/login`.
3. Reads the game with `overrideAccess: false, user`; another studio's game → 404.
4. 303 to `https://discord.com/oauth2/authorize` with:
   - `client_id`;
   - `response_type=code`;
   - `scope=applications.commands webhook.incoming`;
   - `integration_type=0`;
   - `redirect_uri=<NEXT_PUBLIC_SERVER_URL>/api/discord/callback` (the configured URL, never the request's host);
   - `state`.

**The `state` value:**
- It's `base64url({ g: gameID, u: userID, e: now + 600 })`, a dot, then its signature: `sign('discord-oauth-state', …)` with HMAC-SHA256 under `PAYLOAD_SECRET`.
- No cookie is needed: the callback requires the signed-in user to be `u`, which defeats login CSRF and swapped links.

**Callback: `GET /api/discord/callback`**
1. 404 when off; Zod on the query.
2. `error=access_denied` → 303 to the Share tab with `?discord=cancelled`.
3. A bad or expired state → 400 in plain text. No session (it lapsed while the studio was on Discord's screen) → 303 to `/admin/login`, and the studio starts again from the tab. A different signed-in user → 403.
4. Exchange the code: `POST /oauth2/token` with `authorization_code` and the same redirect URI.
   - Zod on the response: it must include `webhook.{id, token, url, guild_id, channel_id}`.
   - The URL must pass `isAllowedDiscordWebhookUrl`.
   - The user's OAuth access token is discarded, never stored or logged.
5. `linkGame` writes `{ guildId: webhook.guild_id, channelId, webhookUrl }` as the user, with `context: { discordLink: true, disableRevalidate: true }`. These fields render nowhere public, so no page changes.
6. Clean up at Discord, best effort, logging failures:
   - once the write has committed, delete the game's previous webhook (§9's compare-and-clear relies on this order);
   - if the write is refused (for example, the studio is suspended), delete the new one.
7. 303 to `gameShareHref(id)` with `?discord=linked`, or `?discord=failed`.

**Disconnect:**
- The Server Action `disconnectDiscord(gameID)` calls `unlinkGame`, which nulls all three fields through the same write path.
- Once that write has committed, it deletes the webhook with `DELETE /webhooks/{id}/{token}`, best effort, and the client calls `router.refresh()`.
- Server Actions check the Origin header, so no extra CSRF token is needed.

**Changing the channel:** run the flow again (the old webhook is deleted), or move the webhook in Discord (Server Settings → Integrations), which keeps its URL.

**Several games in one server:**
- Add critwire from each game's Share tab and pick the same server. Each game gets its own webhook and channel, and `/feedback` asks which game.
- A server may hold games from more than one studio: each person who linked one proved Manage Server there, and game names are public anyway.

#### 5. The interactions endpoint, `POST /api/discord/interactions`

In order:
1. **Off:** 404.
2. **Raw body:** read with `Buffer.from(await req.arrayBuffer())`, and never parsed before verification.
3. **Verification.** Any failure is a 401 with no body and no Sentry event (Discord sends bad signatures on purpose when the endpoint URL is saved).
   - `X-Signature-Timestamp` must be digits, within ±300 s of now. That rejects old and future replays, and needs an NTP-synced clock.
   - `X-Signature-Ed25519` must be 128 hex characters.
   - `crypto.verify(null, timestamp‖body, publicKey, signature)`, with Node's built-in Ed25519. The key is built once from the hex, using the SPKI DER prefix `302a300506032b6570032100`. No dependency is needed.
4. **Parsing:** `JSON.parse`, then a Zod discriminated union on `type`: 1 PING, 2 APPLICATION_COMMAND, 5 MODAL_SUBMIT.
   - `application_id` must be ours.
   - Guild interactions need `guild_id`, `channel_id`, `member.user.{id, username}` and `member.permissions`.
   - Anything else is a 400.
5. **Dispatch.** Every reply is ephemeral (flag 64) and sets `allowed_mentions: { parse: [] }`.

**The 3-second rule:**
- **PING:** answers `{ type: 1 }`.
- **Commands** answer straight away with a form (type 9) or an ephemeral message (type 4).
  - They do at most two indexed queries (`guildGames`), no writes and no Upstash call.
  - A form can't follow a deferred reply, so these must stay synchronous.
- **Form submissions are answered in the request** with an ephemeral message (type 4), after the report is saved. No deferred reply, no `after()`.
  - **Why it fits in 3 s:** the work is two indexed queries (`guildGames`), one Upstash call capped at 1 s (§8), and one `payload.create` in its own transaction. The content filter is local (`obscenity`, no network), and auto-publishing adds a few queries and one insert. That's well under a second on a warm server.
  - **Why it's durable:** the reply goes out only after the create has committed, so a report the player was told about is never lost to a restart. If the process dies first, Discord shows the player "The application did not respond", which is true.
  - **If the work throws:** Sentry, the log, and an ephemeral "Something went wrong, so nothing was sent. Try again." The create's transaction has rolled back.
  - A submission that took over 2 s logs a warning with its duration, so a slow path shows up before players see timeouts.
- **Replays:** a signed request stays valid for up to 300 s, so someone holding one could send it again. Each report stores its interaction ID in a unique column (§7). A replayed submission fails that insert, nothing is created, and the reply is "That was already sent." A replay only uses up a rate-limit slot.
- **Cold start:** the Docker healthcheck (`docker-compose.yml:58-62`) warms Payload within 30 s of boot.

**Logging:** the interaction type, the server, game and report IDs, and the handler's duration. Never usernames, tokens or message text.

#### 6. `/feedback` and "Send to critwire"

**Games for a server: `guildGames(guildId, type)`.**
1. A privileged find of game IDs whose `discord.guildId` matches. An anonymous visitor can't query that field.
2. An anonymous read of those IDs (`overrideAccess: false`, no user), so held games and suspended studios drop out through `publicRead`.
3. Keep the games where `reportRefusal(game, type) === null`.
4. Sort by name and keep at most 25 (a select's limit).

**The forms.**
- Each field is a Label (type 18) holding a Text Input (type 4) or a String Select (type 3), Discord's current form components.
- Discord's limits: 5 fields, a title of at most 45 characters (cut the game's name to fit), and text inputs of at most 4000 characters.

**`/feedback type:<bug|idea>`**
- If no game here takes that type, an ephemeral reply: "This server isn't linked to a game on critwire that takes <bugs|ideas> here." The wording is the same for held, suspended and unlinked games, so nothing leaks.
- Otherwise the form `cw1:fb:<type>:<game>`. `<game>` is the game's ID when there's one game, or `-` when the form has a Game select. At most 5 fields:
  - a Game select, only when there's more than one game;
  - Title (3–160);
  - "What happened" for bugs, "Your idea" for ideas (10–4000);
  - for bugs only: Platform and Game version, optional, at most 120 each.

**"Send to critwire"**
- **Permission:** `BigInt(member.permissions)` must include Manage Messages (`1n << 13n`) or Administrator (`1n << 3n`), or the reply is an ephemeral refusal.
  - This is checked on the server every time. `default_member_permissions` only sets the default, and a server admin can grant the command to anyone in Integrations.
  - `member.permissions` is the member's total in that channel, overwrites included.
- **The message:** `data.resolved.messages[data.target_id]`. If its `content` is empty, the reply is "That message has no text to send."
- **The games:** those that take bugs, `guildGames(guildId, 'bug')`, since the type is picked in the form. The chosen type is checked on submit.
- **The form** `cw1:send:<game>:<messageID>:<authorID>:<authorUsername>`, with `<game>` as for `/feedback`. At most 94 characters, under Discord's 100; the username goes last, so `:` in a legacy name can't break parsing. Its fields:
  - a Game select, only when there's more than one game;
  - a Type select (Bug or Idea);
  - Title, prefilled with the message's first line (at most 160 characters);
  - Details, prefilled with the message's text.

  The moderator can edit both before sending.

**Form submission (answered in the request, §5)**
1. `submittedValues` maps each `custom_id` to its value or values, from either layout (Label or the older Action Row). A change in how Discord shapes submissions can't silently drop a field.
2. **The game, bound to the form:**
   - The game ID comes from `custom_id`, or from the Game select when `custom_id` says `-`. A single-game form never reads a select, and a picker form without its select is a 400.
   - That ID must still be in `guildGames(guild_id, type)`: linked to this server, publicly visible, and taking that type. Otherwise nothing is created and the reply is "That game doesn't take <bugs|ideas> from this server now. Run the command again." (For an import, this is also where an Idea for a game with ideas off is refused.)
   - Another game is never substituted, even when it's now the only one here. A form opened for game A can't send to game B because B was linked while it was open.
   - This also defeats a tampered `custom_id` or select value: nothing in them can route a report to a game that isn't linked to this server and taking that type.
3. **Imports: the permission again.** The submission's `member.permissions` must still include Manage Messages or Administrator, with the same check as above. A moderator who lost the permission while the form was open, or a modified client, can't import.
4. Zod with `reportFieldsSchema`; on failure, a plain reply saying which field is out of range.
5. The rate limit (§8).
6. `createPlayerReport` with category `OTHER`, no email, and `discord: { interactionId, userId, username, messageUrl? }`:
   - `interactionId` is the submission's `id`;
   - for `/feedback`, the player who sent it;
   - for imports, the message's author (from `custom_id`) and `https://discord.com/channels/<guild>/<channel>/<message>`.

   **A replay:** a `ValidationError` from the create, confirmed by a privileged lookup of that interaction ID, means the report already exists; the reply is "That was already sent." This is how `/api/vote` handles its unique index (`api/vote/route.ts:125-127`). Any other error is thrown (§5).
7. The reply:
   - **`/feedback`:** "Thanks, your bug report for **Game** is in. The studio reviews reports before they go on the board." When the hooks published it at once (review off), the second sentence becomes "It's on the board now."
     - The board URL follows, tagged `ref=discord` (`withRef`, `share/kit.ts:41`).
     - A flagged report gets the same text as a clean one, as on the web form.
   - **Imports:** "Sent to critwire as a bug report for **Game**, credited to @user."

The credited author in `custom_id` is only as trustworthy as the moderator, who must still hold Manage Messages when the form is sent. Everything else is checked again.

#### 7. The Discord identity on reports stays private

- **Fields:** a `discord` group on IssueReport, with `userId`, `username`, `messageUrl` and `interactionId`.
- **Access:** create and update use `superAdminFieldAccess`, so studios see the first three read-only; `createPlayerReport` writes with `overrideAccess: true`.
- **`interactionId`:** `unique: true` (a unique index; Postgres allows any number of nulls, so web reports are unaffected). Read is `superAdminFieldAccess` too, since it means nothing to a studio. It exists only to make a replay fail the insert (§5).
- **Admin:** in the sidebar, shown only when set.
- **Why it can't leak:** the collection is already readable only by the studio (tenant-only), and promotion to a public item doesn't copy these fields.
- E2E checks it on anonymous REST, on GraphQL, on the promoted item's REST document and on `feedback.json`, and that the owner's REST read has no `interactionId`.

#### 8. Rate limits

They use `checkRateLimit` (`upstash/rate-limit.ts:24-51`), keyed by Discord user and game, never by IP:

| Command | Key | Identifier | Limit |
|---|---|---|---|
| `/feedback` | `discord-report` | `<discordUserID>:<gameID>` | 5 per 10 minutes |
| Send to critwire | `discord-import` | `<moderatorID>:<gameID>` | 30 per 10 minutes (moderators triage in batches) |

- **Over the limit:** the reply says to try again later, and nothing is created. The check runs after the cheap validation and before the write.
- **Capped at 1 s:** `checkRateLimit` gains an optional `timeoutMs`, passed to Upstash's own `timeout` option (default unchanged at 5 s; `@upstash/ratelimit` `dist/index.js:766`). The Discord keys pass 1000, so a slow Upstash can't push a submission past Discord's 3 s. As on the web forms, Upstash lets a request through when it times out.
- **Without Upstash:** the same as every public endpoint.
  - Production refuses: the reply says Discord feedback isn't available right now, and the refusal goes to the log and Sentry.
  - Development and E2E allow it (`RATE_LIMIT_OPTIONAL`).

**Non-negotiable rule 8 without Turnstile.** Turnstile proves a human is at a browser, which Discord can't relay. Instead:
- the signature proves the request comes from Discord for a signed-in Discord account, behind Discord's own anti-abuse checks and the server's verification level;
- the limit applies per account and per game;
- every report still passes the content filter and, by default, the review queue.

#### 9. Posts to Discord

**When a job is queued.** Two `afterChange` hooks queue posts in the write's transaction (through `req`), via `queueDiscordPost`. It returns early unless Discord is on and the game has a webhook.
- The webhook check is `gameWebhook(gameID, req)`: one primary-key read with `overrideAccess: true`, as `autoPublishReport.ts:25-32` reads its game. It passes `req` only to stay in the write's transaction.
- It must be privileged: the writer may have no user (any Local API or job write), and `tenantMemberFieldRead` would then hide the URL and silently skip the post.
- **Updates (`queueDiscordUpdatePost`):** when an update *becomes visible*, meaning it is now `_status === 'published' && !flagged` and wasn't before.
  - That covers a first publish, a republish, and a super admin approving a held update.
  - Saving a draft or editing a published update doesn't count.
- **Feedback items (`queueDiscordStagePost`):** on update only, never on create. It queues when `publicStage(status)` changes, the new stage is Planned, In progress or Shipped, and the item is public.
  - Drags within one stage, writes that only change `_order`, and creations never queue.
  - Posts announce stage changes only, not new public items (the review's question 4 is unanswered; this is the conservative choice).
- **Both:**
  - `waitUntil: now + 60 s`;
  - concurrency key `discord-update:<id>` or `discord-stage:<id>`, with `supersedes: true` and the default `exclusive`.

  Each change pushes the post back to 60 s after the latest change, and the per-minute autorun sends it 60–120 s after the last one.

**When a job runs** (`discord-update-post`, `discord-stage-post`). The steps below run in order, and any "no" completes the job with `{ posted: false }`:
1. Discord is on.
2. **The subject, read as an anonymous visitor (F5):** the update or item by ID with `overrideAccess: false` and no `req` or user. Drafts, held updates, private items, held games and suspended studios all fail here through `publicRead`. Then its game is read the same way, for the name and slug.
3. For stage jobs, the current stage is Planned, In progress or Shipped.
4. **The post log** (privileged reads, without the job's `req`):
   - an update with any `discord-posts` row is done;
   - an item whose latest row has the same stage is done, so a quick round trip or a re-drag posts nothing.
5. `gameWebhook(gameID)`: a privileged read (`overrideAccess: true`, without the job's `req`) that returns only the URL. If there's none, the job is done.
6. **`executeDiscordWebhook(url, …)`:**
   - **`DiscordWebhookGoneError`** (the webhook was deleted in Discord): `stopPosting(gameID, url)` clears `channelId` and `webhookUrl` and keeps `guildId`, but only if the stored webhook is still `url`. The job logs at info level and completes.
     - **Compare and clear:** one `payload.update` on `game-projects` with `where: { and: [{ id: { equals: gameID } }, { 'discord.webhookUrl': { equals: url } }] }`, so a link made since the job read `url` is never touched.
     - **Why that's enough:** critwire deletes an old webhook only after the replacing link or the unlink has committed (§4). So by the time the old webhook answers 404, the stored URL is already different and nothing matches. The one gap left is under Risks.
     - **Authorized on its own:** `overrideAccess: true`, no `req` and so no user. The queue runner's user changes nothing, and `enforceTenantWrite` lets user-less system writes through (`tenantWrite.ts:20-23`). It passes `context: { discordLink: true, disableRevalidate: true }`, since the fields render nowhere public.
   - **Any other failure** throws and is retried (`retries: { attempts: 3, backoff: { type: 'exponential', delay: 60_000 } }`), with Sentry. After the last attempt the job keeps its error for a super admin (`docs/patterns.md`, Jobs).
   - **Discord's limit:** a webhook takes about 30 posts a minute. The autorun runs at most 10 jobs a minute (`payload.config.ts:146`), so bulk triage stays under it, and a 429 throws and retries like any other failure. Don't raise the autorun's limit without checking this.
7. **Record the post** in `discord-posts` (a privileged create, without the job's `req`). The post comes before the record, so a crash in between gives a duplicate post on retry, never a silent miss.

**What a post says:** one embed each, never with the reporter's identity.
- **Update:** the author line is the game's name; the title is `updateFeedTitle(note)` (`patchNotes.ts:18-19`); the link is the update's page tagged `ref=discord`; the description is the summary, cut to 300 characters.
- **Stage:** the author line is the game's name; the title is the item's title; the link is the item's page tagged `ref=discord`; the description is "Now planned", "Now in progress" or "Shipped".

#### 10. Data model and migration

- **GameProject:** the `discord` group, 3 columns, with `guild_id` indexed.
- **IssueReport:** the `discord` group, 4 columns, with `interaction_id` under a unique index.

#### 15. The project's rules, and how this design keeps them

- **Payload conventions:** hooks queue, access decides visibility, and all data goes through the Local API.
- **Tenant scoping:** done by the plugin. The link writes run as the user. The privileged operations are named helpers: reads that return IDs or a URL, the post log, and `stopPosting`, which only clears a link whose webhook just failed.
- **Zod at every boundary:** interactions, the callback query, Discord's token response and the form values.
- **Revalidation:** nothing here mutates published content, except a report that auto-publishes, which goes through the existing hooks. Link writes pass `disableRevalidate` because the fields render nowhere public.
- **Access control on every collection:** `discord-posts` is `superAdminOnly`, and the new fields have field-level access.
- **Rate limit and Turnstile:** see §8.
- **No speculative pieces:** no gateway, no bot token, and no settings toggles.

### Rejected alternatives

- **Gateway bot:** needs an always-on process; out of scope.
- **Bot-token posting with a channel picker in critwire:** needs a bot token, Discord's channel-list API and channel permissions, and gives the studio more steps.
- **A pasted webhook URL field:** one more studio step, and it doesn't link a server for `/feedback`.
- **Commands registered per server:** needs a bot token, and a resync on every game change.
- **An autocomplete `game` option:** another interaction type, and an optional option is still ambiguous when the player skips it. A select in the form is one step.
- **Merging changes or de-duplicating posts in Upstash:** Upstash is optional, and Payload's jobs already provide `waitUntil` and `supersedes`.
- **Post state as fields on Issue and PatchNote:** PatchNotes are versioned (F6), and two mechanisms would be worse than one log.
- **Deferring form submissions and finishing them in `after()`** (the first design): a restart between the answer and the work loses a report, and nothing retries it.
- **A queued job per form submission:** durable, but it stores the 15-minute interaction token in `payload_jobs`, and adds a task, a reply edit and retries for work that takes well under a second.
- **Checking the interaction ID with a find before the create, without a unique index:** two replays at once both pass the check.
- **A raw SQL compare-and-clear through `payload.db.drizzle`:** skips the collection's hooks for a gap the write ordering already closes (§9, Risks).
- **Merging `actions.ts` into `link.ts`:** every export of a `'use server'` file becomes a callable endpoint, which would expose `linkGame` and `stopPosting`.
- **Deleting a game's webhook in an `afterDelete` hook:** an HTTP call inside the delete's transaction, for a webhook nothing posts to any more. Deferred (Risks).
- **`discord-interactions` or `tweetnacl`:** Node's `crypto` verifies Ed25519 natively.
- **A command-registration script:** the Docker image can't run scripts, and syncing at boot needs no operator step.
- **The `bot` scope:** adds a bot member and a permissions prompt for nothing we use.
- **A production setting for the post delay:** E2E moves `waitUntil` forward instead.

### Risks and open questions (each with the conservative default chosen)

1. **Combining `applications.commands` with `webhook.incoming` in one authorization (uncertain).**
   - Discord documents both scopes and the webhook object in the token response, but I can't confirm that one consent screen shows both the server and the channel pickers.
   - **Default:** the single flow above, with the server taken from `webhook.guild_id`.
   - **Fallback, if the owner's test (H14 step 9) shows otherwise:** two buttons, "Add the commands" (`applications.commands`) and "Choose the posts channel" (`webhook.incoming`), on the same callback.
2. **Labels and string selects in forms (fairly sure; they shipped in 2025).**
   - The parser accepts both the Label and the Action Row layouts.
   - If Discord rejects selects in forms, the fallback is a required `game` autocomplete option on `/feedback`, and a Type select sent as an ephemeral message before the import form.
   - Nothing in this mission talks to the real Discord, so H14 step 9 is the first real check. It's listed there.
3. **The message's text in the message command (fairly sure).** Discord documents the target of a message command as exempt from the Message Content intent. If the text comes back empty, the reply says so and nothing is created.
4. **"Public Bot" and server-count verification for an app without a bot user (uncertain).** Covered by H14 steps 5 and 10.
5. **Cloudflare challenging Discord's POSTs:** saving the endpoint would fail. Covered by the docs and H14 step 8.
6. **Raids:** many fresh Discord accounts could each send 5 reports. Review is on by default, so nothing goes public, and the studio can remove the app or dismiss the reports. There's no per-game cap yet, because the Brief asks for per-user-per-game limits.
7. **A duplicate post after a crash between posting and recording:** accepted. A missed post would be worse.
8. **More than 25 games linked to one server:** the picker shows the first 25 by name, as documented.
9. **The F1 race in production: a known, unresolved defect.** This mission fixes the test only. Until the owner answers H15, the default (c) stands, and a page can stay stale for up to an hour after a write that races a visitor's render.
10. **A submission slower than 3 s.** Discord shows the player an error although the report was saved. A retry is a new interaction, so it can make a second report. The rate limit bounds it, review catches it, and the 2 s warning shows it in the log. **Default:** accept; revisit only if the warning appears.
11. **A manual webhook deletion racing a relink.** `stopPosting`'s `where` is a read, then a write by ID: Payload's `update` finds the matching IDs and updates each one (`payload/dist/collections/operations/update.js`). If the studio deletes the webhook in Discord itself, and a relink commits in the same milliseconds as the job's 404, the new link could be cleared. The tab then says posts are off, and adding critwire again fixes it. **Default:** accept.
12. **A deleted game's webhook stays in the studio's server.** Nothing posts to it. `docs/discord.md` says to remove it in Server Settings → Integrations. **Default:** no hook (Rejected alternatives).

## Architecture review (Astra)

## Decisions

- **2026-10-02 · Posting goes through the webhook Discord creates at install (`webhook.incoming`), with no bot user or bot token.** The studio picks the server and the channel on Discord's own screen in one authorization (`applications.commands webhook.incoming`). That's the fewest studio steps, and critwire holds no bot token. To change the channel, the studio adds critwire again or moves the webhook in Discord.
- **2026-10-02 · `/feedback` takes Bug or Idea as a command option, not as a field in the form (minor deviation from the Brief's wording).** This lets the form ask for platform and version on bugs only, and keeps the game picker within Discord's 5-field limit. The game, and the type for message imports, are string selects in the form.
- **2026-10-02 · Discord posts wait 60 s and quick changes merge.** Each change replaces the pending post (Payload concurrency `supersedes`), and the per-minute autorun sends it. This replaces Must-fix 5's "run right after queueing". A super-admin-only `discord-posts` log makes it one post per update and one per public stage. Posts cover stage changes only, not new public items, and when a job runs it reads its subject as an anonymous visitor, so `publicRead` decides what's held, suspended or private.
- **2026-10-02 · Rate limits:** `/feedback`, 5 per 10 minutes per Discord user per game; Send to critwire, 30 per 10 minutes per moderator per game. Production without Upstash refuses, as the public forms do.
- **2026-10-02 · Commands register at boot.** A client-credentials token and a bulk overwrite, fire-and-forget, so there's no operator step and the Docker image needs no script.
- **2026-10-02 · A webhook deleted in Discord stops posting for that game** (channel and webhook cleared, server link kept) instead of failing jobs forever. The Discord tab says so.
- **2026-10-02 · The baseline flake (`patch-notes.spec.ts:265`) is fixed in the test.** The spec waits for the feed page's prefetches before it unpublishes. The production race it exposed is real (Next stamps ISR entries when they're written) but narrow, so it goes to the owner as H15, with "leave as is" as the default.
- **2026-10-02 · Discord form submissions are answered in the request, after the report is saved, and one interaction makes at most one report.** This revises the first design, which answered at once and did the work in `after()`, where a restart could lose a report (Astra must-fix 2). The work fits Discord's 3 s: two indexed queries, one Upstash call capped at 1 s, one create. A unique, super-admin-only `IssueReport.discord.interactionId` turns a replayed request into "That was already sent." A form is also bound to the game it was opened for.
- **2026-10-02 · Discord post jobs run on their own `discord` queue** (planner finding, accepted at the Steps stage). E2E's two servers share one database and both autorun jobs, so on the `default` queue the Discord-off server could claim a due post and complete it unsent. `jobs.autoRun` adds the `discord` queue only when `isDiscordOn()`. Deviation from §2: a post queued before Discord is switched off now waits in the queue instead of completing with `{ posted: false }`; harmless, since nothing is sent either way.
- **2026-10-02 · Modules the Payload config imports never import `@payload-config`** (S9, deviation from §1's module table). The post hooks and jobs are part of the config, so `link.ts` takes `payload`/`req` from its callers and `guildGames` lives in `feedback.ts`, its only caller; `updateFeedTitle` moved to a database-free module. An import cycle through the config would only work while every use stays lazy.
