# Mission: critwire reach (links, buttons, badge, framing, referrals)

This file is the mission's state. Agents: follow "In a mission session" in `~/.claude/CLAUDE.md`, and keep this file current.

## Brief


### Goal

Every studio can put critwire on the pages it already has, including the ones that only accept links and images (Steam, itch.io, free Carrd, Linktree, READMEs). When this mission is done:

1. **A "Put critwire on your site" panel.** It replaces "Share this link" as the first next step after onboarding (`src/lib/onboarding/nextSteps.ts`), and also appears on each game's admin dashboard. It is built so later missions can add an "Embed" tab and a "Discord" tab. This mission ships the "Links and buttons" content, with:
   - **Canonical public URLs** with copy buttons: hub, feedback list, board, updates and RSS. Add a friendly alias, `/g/<game>/roadmap`, which redirects to the board view.
   - **Hosted button images** ("Give feedback", "Roadmap", "What's new"): light and dark, PNG and SVG.
   - **Ready-to-paste snippets per platform:** HTML (Carrd, Linktree, custom sites), Markdown (READMEs, itch.io) and Steam BBCode (announcements).
   - **Steam guidance:** on Steam, the place to use is the store page's Website field plus links in announcements. Steam doesn't allow outside links in the store description.
   - **Referral tags:** every kit link carries `?ref=<platform>`.
2. **A live badge** at `/g/<game>/badge.svg` and `/g/<game>/badge.png`, showing counts per public stage (for example "12 open · 3 planned") and the latest update's version.
   - It follows the game's theme and is cached for at most 5 minutes.
   - It never reveals a held game or a suspended studio. Return a neutral image, not an error, so host pages don't show a broken image.
3. **The app owns its framing policy.**
   - Every portal and admin page sends `Content-Security-Policy: frame-ancestors 'self'`.
   - Remove `add_header X-Frame-Options SAMEORIGIN` from `nginx.conf` (line 40), so the app's policy is the only one, and update `docs/deploy.md`. Keep the other nginx headers.
   - The embed mission will later allow framing on embed routes only.
4. **"Where players come from."** Count referrals per game, per day and per `ref` source, with no personal data, and show the last 30 days in the game's admin.
   - Cached pages ignore query strings on the server, so count with a tiny client-side ping to an endpoint, not from page renders.
   - On an instance with Upstash, count there. Never write to Postgres on every page view on the hosted instance. Without Upstash, the counter may be off and say so.

### Why

Studios already have a presence: a Steam page, itch.io, Discord, sometimes a website. Critwire must show up there, not ask studios to send players somewhere new. Most of those places accept only links and images, so links, buttons and a live badge reach the most studios. The referral counts show which places actually bring players. The framing fix is a prerequisite for the embed mission that follows this one.

### Findings

Ranked by impact. Each one was checked in the code. "Fine as is" lists the areas I checked and am leaving alone.

**F1 · High · bug: the framing policy exists only in nginx.** `nginx.conf:40` sends `X-Frame-Options: SAMEORIGIN`, and the app sends nothing: `next.config.ts:11-48` has no `headers()`, and `src/` has no middleware or `proxy.ts`. This causes three problems:
- Anything served without this nginx can be framed, admin login and vote buttons included. That covers the demo on port 3000 and a self-hosted instance behind another proxy, so clickjacking is possible there.
- The E2E suite runs `next start` without nginx, so it never sees the production policy.
- `X-Frame-Options` can't express the embed mission's exemption for a single route.

Fix: see Goal 3 below.

**F2 · High · existing bug, not fixed in this mission: in production, per-IP rate limits are keyed on Cloudflare's edge IP, not the player's.**
- `nginx.conf:52` sets `X-Real-IP $remote_addr` without `real_ip_header` or `set_real_ip_from`, and `getClientIP` (`src/lib/public-forms/request.ts:3-9`) reads `x-real-ip` first.
- Behind Cloudflare's proxy (`docs/deploy.md`, step 6), `$remote_addr` is a Cloudflare edge address. So every player who comes through the same edge shares one budget; for votes that's 10 a minute (`src/app/api/vote/route.ts:33-38`).
- With no proxy in front (the demo), a client can set its own `X-Real-IP` and avoid every limit.
- The referral beacon inherits all of this.

Fix: make nginx trust `CF-Connecting-IP` only from Cloudflare's IP ranges. That needs Cloudflare's published IP list and a change to production nginx, so it goes to the owner as proposed handoff **H-A** below. H-A is the operational prerequisite for accurate per-IP limits, the referral counter's included. Raising a limit doesn't fix a shared edge, so the referral limit stays sized for one visitor, and the docs state the undercount until H-A is done.

**F3 · Medium · DRY and SRP, plus a bug: the "Share this link" step is special-cased in two places, and they build its URL from different origins.**
- `nextSteps.ts:10-21` gives `href` two meanings: for `share` it's the hub path, which callers prefix with an origin; for every other step it's an admin URL.
- So `WelcomePanel.tsx:64-78` and `StudioDashboard.tsx:69-77` both branch on `step.key === 'share'`.
- The welcome panel takes the browser's origin (`getClientSideURL()`, `WelcomePanel.tsx:16`), while the dashboard uses the configured `NEXT_PUBLIC_SERVER_URL` (`StudioDashboard.tsx:22`). A studio that opened its portal on another host (a raw IP, or an alternate domain) is told to share that host.
- The step's text is also wrong for Steam. `nextSteps.ts:19` says to put the link on "your store page", but a Steam store description can't link to other sites.

Fix: `share` becomes an admin link like the other steps, pointing to the game's Share view. Every kit URL uses the configured origin, and the welcome panel renders the kit panel.

**F4 · Medium · DRY: there is no helper for absolute URLs, and the board URL isn't in `portalPaths`.**
- `${getServerSideURL()}${path}` is concatenated by hand in six places: `StudioDashboard.tsx:22`, `jobs/contact.ts:95` and `:149`, `updates/feed.xml/route.ts:34-41`, `g/[gameSlug]/page.tsx:54`, and `authEmails.ts:9` (which has its own `link()`).
- The board URL is built separately as `feedbackHref(…, { view: 'board' })` (`MarketingHome.tsx:21`).
- The kit needs five absolute URLs per platform.

Fix:
- `portalPaths` gains `board`, `roadmap` and `badge(format)`.
- `src/utilities/getURL.ts` gains `absoluteURL(path)`, which concatenates the path onto `getServerSideURL()` the same way the existing call sites do.
- New code, and the files this mission touches, use both. Other call sites move over the next time they're touched, so there's no churn now.

**F5 · Medium · test gap: no E2E test has ever exercised an Upstash code path.** E2E sets Upstash to empty values (`tests/e2e/support/env.ts:98-99`). `RATE_LIMIT_OPTIONAL=1` only turns production's refusal into "allow" when Upstash is missing (`src/lib/upstash/rate-limit.ts:31-35`); with Upstash configured, the flag does nothing. The referral counter must be tested against Upstash. Fix: an Upstash stand-in for E2E (see Goal 4 and E2E coverage). It also answers `@upstash/ratelimit`'s sliding-window call with "allowed", so on port 3100 every rate-limited route goes through the real Upstash client, and `RATE_LIMIT_OPTIONAL` keeps today's meaning. The limits themselves stay untested, which is out of scope.

**F6 · Low · DRY, latent: the public per-stage filter is written inline twice.** It's in `queryPublicIssues` (`src/lib/game-portal/issues.ts:41-48`, the list's `?stage=`) and `queryBoardColumn` (`:89-94`), and the badge needs it a third time. Copies would let the badge's counts, a board column's count and the filtered list the column links to drift apart.

Fix: extract `publicIssuesWhere({ projectID, stage?, type? }): Where[]` in `issues.ts`, and use it in all three. It returns:
- the game and `isPublic`;
- that stage's statuses, or "not archived" when there's no stage;
- the type, when given.

`statusesFor(stage)` never contains an archived status (`stages.ts:19-44`), so the list's results don't change. `queryTopFeedback` and `queryShippedFeedback` keep their own fixed rules: they aren't a visitor-chosen stage, and no count is compared with them.

**F7 · Medium · bug (cross-site request forgery): `/api/vote` accepts form posts from other sites.** `src/app/api/vote/route.ts:43` parses `req.json()` whatever the `Content-Type`.
- Any site can auto-submit a `<form method="post" enctype="text/plain">` whose body is valid JSON: `{"issueId":5,"x":"="}`. Zod strips the extra key.
- The `SameSite=Lax` vote cookie isn't sent on a cross-site POST, so the route mints a new token and casts a vote for every visitor of that page, up to the per-IP limit.
- The planned referral endpoint had the same hole (both reviews).

Fix: `isJSONRequest(req)` (below), checked before parsing in both routes, answering 400 otherwise. `VoteButton.tsx:35` already sends `application/json`, so real votes are unaffected.

**Fine as is (reused, unchanged):**
- **Public gate.** `getGameProject` reads with `overrideAccess: false`, and `publicRead.ts:17-26` drops held games and suspended studios through relationship paths. The badge and the beacon both reuse this.
- **Revalidation.** No new surface keeps a server-side cache: the badge and buttons are dynamic with short HTTP caching, and the alias is a config redirect. So no hook changes are needed.
- **Theme.** `resolveProjectTheme` (`projectTheme.ts:15-23`) already falls back to the default theme, with a Sentry report, when a stored theme is invalid.
- **Admin access.** Payload's document view loads the document as the signed-in user with `overrideAccess: false`, and redirects to the list when it can't (`@payloadcms/next/dist/views/Document/index.js:78-99`). A custom document view therefore inherits the multi-tenant plugin's scoping.
- **Payload headers.** `withPayload` merges a project's `headers()` with its own (`withPayload.js:91-105`).
- **Rasterizing.** `sharp` 0.34.2 is already a dependency and turns path-only SVG into PNG on this arm64 host (I checked: SVG to a 2× PNG). The Docker runner (`node:24-alpine`) has no fonts, so SVG `<text>` would render blank there.

#### Image rendering (server only, shared by the buttons and the badge)

`src/lib/share/images.ts`:
- **Text as paths.** Text is drawn as glyph paths with `opentype.js` 1.3.4, pinned exactly, with `@types/opentype.js` (1.3.x) as a dev dependency. It's MIT and pure JS.
  - 1.3.4 has had four and a half years of use (October 2021).
  - 1.3.5 (2026-04-29) isn't a small patch, despite its number. It's a rebuild from the 2.0 line: new bundle entry points, its two dependencies inlined, sources dropped. It came out a week before 2.0.0 (2026-05-06, now `latest`).
  - The Steps must put this reason beside the pin, so it isn't bumped casually.

  The font is `src/lib/share/fonts/DejaVuSans.ttf`, plus its `LICENSE`, both copied from this VPS's `fonts-dejavu-core` package (`/usr/share/doc/fonts-dejavu-core/copyright`). It's permissive, covers wide Unicode ranges, and is the classic badge face. It's read once per process with `readFileSync(path.join(process.cwd(), …))`.
- **The font must reach the Docker image.** `next.config.ts` gets an `outputFileTracingIncludes` entry for the badge and button routes, so the font is included in the standalone output.
- **SVG output.** `badgeSVG(model)` and `buttonSVG(id, scheme)` produce SVG with a width, height and `viewBox`, `role="img"`, and an `aria-label` plus `<title>` holding the escaped text. It has no `<text>`, no scripts and no external references. Path glyphs render the same in every viewer and in sharp, whether or not the server has fonts. The `<title>` is what E2E reads.
- **PNG output.** `toPNG(svg)` uses sharp at density 144, which gives a 2× PNG.
- **Memoized constants.** The 12 button images and the neutral badge (SVG and PNG) depend only on constants. Each is rendered once per process and kept in a module-level `Map`. This memoizes a pure function, it doesn't cache data, so there's nothing to revalidate.
- **Responses.** `imageResponse(svg, format, maxAgeSeconds)` builds the `Response` with `Content-Type` and `Cache-Control: public, max-age=N, s-maxage=N`. There's no `stale-while-revalidate`, so the cache bound is exact.

#### Goal 2 · The live badge

- **Routes.** `src/app/(public)/g/[gameSlug]/badge.svg/route.ts` and `badge.png/route.ts` are both thin: `imageResponse(await gameBadgeSVG(slug), fmt, 300)`, with `dynamic = 'force-dynamic'`. Route handlers don't run the portal layout's gate.
- **`src/lib/share/badge.ts`, `gameBadgeSVG(slug)`.** It calls `getGameProject(slug)`, the established public read for route handlers. A `null` result (unknown slug, held game or suspended studio) returns `neutralBadgeSVG()`. Otherwise it fetches three things in parallel:
  - `countPublicIssuesByStage(projectID)`, new in `issues.ts`: one `payload.count` per entry in `PUBLIC_STAGES`, with `overrideAccess: false` and `publicIssuesWhere({ projectID, stage })` (F6). Private and archived items, and internal statuses, are never counted.
  - `getLatestVersionLabel(projectID)`, new in `patchNotes.ts`: the newest published update (`-publishedAt`) that has a version label. It reads through access, so held updates and drafts are skipped. The label is trimmed and cut to 24 characters.
    - The filter needs both `{ versionLabel: { exists: true } }` and `{ versionLabel: { not_equals: '' } }`.
    - Payload compiles `not_equals` to `IS NULL OR <> ''` (`@payloadcms/drizzle` `parseParams.js:225-226`). Without `exists`, a newer update with no version would hide an older one's version.
  - `resolveProjectTheme(project)`.
- **Text.** The label segment reads `feedback`. The value segment lists each stage with a non-zero count, in stage order, as `"<n> <stage label in lower case>"` joined by ` · `, followed by ` · <version>`. For example: `12 under review · 3 planned · 1 in progress · v1.4`.
  - With no feedback it reads `no feedback yet`, plus the version if there is one.
  - It uses the public stage names, not the brief's example "open", so players only ever see one vocabulary.
- **Theme.**
  - The label segment uses `accent` with `accentForeground`, and the value segment `surface` with `foreground`. The theme schema already guarantees 4.5:1 contrast for both pairs.
  - The outline is `border`, and the corner radius follows `shape` (sharp, balanced or soft).
  - The game's display typography doesn't carry over; the badge always uses DejaVu.
- **Neutral image.** It reads `feedback` / `unavailable` in fixed greys, with status 200, and is memoized. Unknown, held and suspended all return byte-identical images, so an unknown slug costs one indexed read. That way a host page never shows a broken image, and the badge reveals nothing, not even whether the game exists. (The portal itself already distinguishes `/unavailable` from a 404; the badge doesn't add to that.) `docs/patterns.md` records this as a deliberate exception to "route handlers answer 404".
- **Caching.**
  - Every answer is cached for 300 seconds (`max-age=300, s-maxage=300`).
  - There's no server cache, so there's nothing to revalidate. A hold, suspension or edit reaches every viewer within 5 minutes, the same bound media already uses (`docs/architecture.md`, Media serving).
  - **Query strings.** The kit never adds one to an image URL, but anyone can: `?v=2` cache-busters, or a flood of random ones. Each would be another cache key at Cloudflare, and another render with about 7 reads.
    - So a badge request with any query string gets a `308` to the bare badge URL, with `Cache-Control: public, max-age=86400`.
    - The route decides this from `req.url`, before any read.
    - That keeps one cache key per game and format. Browsers follow redirects for images.
    - Buttons don't need this, because they're memoized.
  - Cloudflare caches `.svg` and `.png` by default and honours `s-maxage`. So the origin renders at most once per URL per edge every 5 minutes, about 7 short indexed reads each time.
  - I rejected an ISR route handler because Next would add `stale-while-revalidate` up to `expireTime` (a year).

#### Goal 4 · Where players come from

- **Store.** `src/lib/referrals/counter.ts` (server only):
  - `isReferralCounterOn()` is `getRedis() !== null`.
  - `recordReferral(gameID, source)` is a command returning `void`. It runs one MULTI: `HINCRBY referrals:<gameID>:<YYYY-MM-DD UTC> <source> 1`, then `EXPIRE <key> 3024000` (35 days, so 30 full days plus today stay readable). Each hit resets the TTL, so a day's key lives 35 days after its last hit, at most 36 days after the day began. That's harmless, and `docs/integrations.md` says so.
  - `readReferrals(gameID, days = 30)` is a query: one pipeline of 30 `HGETALL`, returned newest first.
  - Keys use the game's ID, not its slug, so renames keep the history and a reused slug doesn't inherit another game's counts. Only counts are stored.
- **Endpoint `POST /api/referrals`** (`src/app/api/referrals/route.ts`), shaped like `/api/vote`. It handles a request in this order:
  1. Unless `isJSONRequest(req)`, it answers 400 without reading the body.
  2. It validates the body with Zod, `{ game: z.number().int().positive().max(2147483647), ref: z.enum(REF_SOURCES) }`, and answers 400 if that fails.
  3. If the counter is off, it answers 404, as the signup routes do when signup is off.
  4. It runs `checkRateLimit({ identifier: '<ip>:<game>', key: 'referral', limit: 60, windowSeconds: 60 })` and answers 429 when the limit is hit.
  5. It runs `payload.count({ collection: 'game-projects', overrideAccess: false, where: { id: { equals: game } } })`. Zero means the game is held, suspended or unknown, and it answers 404.
  6. It calls `recordReferral` and answers 204.

  Any failure is sent to Sentry, logged with pino, and answered with a 500. There are no Postgres writes; there's one indexed read, and only for views that carry a `ref`.

  **Cross-site requests stay impossible from browsers.**
  - A form, or a `fetch` in `no-cors` mode, can only send CORS-safelisted types (`text/plain` and the form encodings). Step 1 rejects all of them.
  - A cross-site `fetch` with `application/json` needs a preflight. The route exports only `POST` and sets no `Access-Control-*` header. Next answers `OPTIONS` itself with a 204 that has only an `Allow` header (`next/dist/server/route-modules/app-route/helpers/auto-implement-methods.js:66-73`), so the preflight fails and the browser never sends the POST.
  - Payload's `cors` list (`payload.config.ts:105`) applies only to Payload's own REST handler, and it names only this site's origin anyway.

  **No Turnstile:** rule 8 is about forms, and a beacon has no user input. Turnstile would mean a challenge, and a third-party script, on every portal page view. Validating against the whitelist and the public game, plus the rate limit, caps the damage. The admin presents the counts as a guide.
- **The ping.** `src/components/game/ReferralPing.tsx` is a client component with props `{ gameID }`.
  - `PortalFrame` renders it only when `isReferralCounterOn()`, the same "read the environment when rendering" pattern as `PortalFooter`'s `isOpenSignup()`.
  - It's wrapped in `<Suspense fallback={null}>`, as the hub already does for `WelcomePanel` (`g/[gameSlug]/page.tsx:33`), because `useSearchParams` needs a boundary on prerendered pages.
  - It's in the layout, so every portal page counts, whether ISR or SSR.

  **Trigger: every navigation, not only mount.** The layout stays mounted across client-side navigation within a game, so a mount-only effect would miss tagged URLs reached that way (Astra). The ping has one effect whose dependencies are `usePathname()` and `useSearchParams()`. Next updates both on every navigation (`<Link>`, `router.push`, back and forward), so the effect runs once per navigation.

  **Consume.** The effect reads `ref` from the live `window.location`, not from the hooks' snapshot. If `ref` passes `isRefSource`:
  1. It first removes `ref` with `window.history.replaceState(null, '', urlWithoutRef)`, keeping the other parameters (`view=board`, for example). Next 16 patches `replaceState` to keep its router state and update `usePathname` and `useSearchParams` without a server request (`next/dist/client/components/app-router.js:268-279`).
  2. Then it sends `fetch('/api/referrals', { method: 'POST', keepalive: true, headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ game, ref }) })`.

  **Dedupe: the URL is the token.** Removing `ref` before sending means each arrival at a tagged URL counts exactly once. None of these find a `ref` to count:
  - the effect run caused by the strip itself;
  - StrictMode's second run in development;
  - a reload;
  - back or forward to the replaced history entry;
  - a copied address.

  A new navigation to a tagged URL is a new arrival and counts again. Values that fail `isRefSource` (`?ref=nope`) are left in the URL and never sent.

  The ping ignores the response, because a beacon must never affect the page; the server records any failure.
- **Admin.** `src/components/admin/share/ReferralCounts.tsx` is a server component placed under the panel in the Share view, titled "Where players come from".
  - **Counter off:** "Referral counting is off on this instance. It needs Upstash Redis (see docs/self-hosting.md)."
  - **Counter on:** a table of the last 30 UTC days. Each row is a day with visits, newest first; there's one column per source that appears, plus a totals row. Labels come from `SHARE_PLATFORMS`, with a note that tags come from links, so the counts are a guide.
  - **Upstash fails:** the error goes to Sentry, the section shows "Couldn't load the counts right now", and the kit above stays usable.
- **Rate limits are unchanged.** `RATE_LIMIT_OPTIONAL` keeps today's meaning: it only turns production's refusal into "allow" when Upstash is missing (`rate-limit.ts:31-35`). Production enforcement, and the app's rate-limit code, don't change. Port 3100 now has Upstash configured (the stand-in), so its rate-limited routes go through `@upstash/ratelimit`, and the stand-in answers that library's sliding-window call as "allowed" (see E2E coverage). Port 3102 keeps empty Upstash plus the flag, as today.

### Rejected alternatives

- **Middleware or `proxy.ts` for the CSP:** AGENTS.md forbids custom proxy patterns, and `headers()` covers every route.
- **Keeping `X-Frame-Options` beside the CSP:** that's two policies, and `X-Frame-Options` can't exempt the embed routes.
- **`next/og` `ImageResponse`:** it makes PNG only, on a fixed canvas, which doesn't suit a badge whose width varies. I'd need a second renderer for SVG.
- **SVG `<text>`, with sharp rasterizing using server fonts:** the Alpine runner has no fonts. E2E on this VPS would pass while production showed blank text.
- **satori through Next's internal `compiled/@vercel/og` path:** it isn't a public API.
- **Committed button PNG and SVG files:** generated binaries drift away from the renderer. A route can share the badge's renderer instead.
- **ISR or `unstable_cache` for the badge:** that adds a year of `stale-while-revalidate`, or a second layer of staleness, plus hook wiring, for an image allowed to be 5 minutes old.
- **A 404 for unknown or held badges:** host pages would show a broken image, and the response would separate unknown games from held ones.
- **Counting in Postgres, or in server renders:** the brief forbids writes on page views, and cached pages never run server code for a query string.
- **Free-form `ref` values:** they make an unbounded key space and noisy data.
- **Turnstile on the beacon:** it's a challenge and a third-party script on every page view, for something that isn't a form.
- **An in-memory referral store for E2E:** test code would ship in production, and the Upstash code path would stay untested until deploy.
- **A local Redis with a REST proxy:** this VPS has no Redis and no Docker.
- **The full panel on the global dashboard for every game:** the dashboard gets heavy, and Payload's document view is the established page for one game.
- **A tab registry for later tabs:** it's speculative; each later tab is its own component.
- **A 301 for `/roadmap`:** browsers cache it permanently, which pins the alias to the board.
- **The nginx check as an E2E spec:** E2E never runs nginx. It's a file invariant, which is exactly what `tests/int` is for.
- **Making `RATE_LIMIT_OPTIONAL` turn limits off even with Upstash configured** (the first design): a stray flag in production would silently drop every limit. The stand-in answering the sliding-window call keeps production code unchanged.
- **Refusing to boot when that flag is set in "real" production** (Fable): moot, since the flag keeps today's meaning, and detecting "real" production from Sentry or Resend keys would be guesswork.
- **A real sliding window in the stand-in:** existing specs (S4.6's parallel votes, and many specs posting from one IP) would hit limits. Testing the limits is out of scope.
- **A mount-only ping** (the first design): it misses tagged URLs reached by client-side navigation inside the persistent layout.
- **`router.replace` to strip `ref`:** it's a soft navigation that fetches the page's server payload again. `history.replaceState` updates the URL and Next's hooks with no request.
- **Deduping with `sessionStorage`, or a stored "last URL counted":** the stripped URL already is the token, and a stored key would wrongly skip a genuine second arrival.
- **`includes('application/json')` for the JSON check:** `text/plain; x=application/json` is CORS-safelisted, so it would pass without a preflight.
- **Checking `Origin` on `/api/referrals` as well:** with JSON only and no CORS headers, browsers can't send it cross-site, and non-browser clients can forge any header.
- **Ignoring badge query strings instead of redirecting:** every unique query would still cost a render and about 7 reads. A Cloudflare "ignore query string" rule needs the dashboard and does nothing for self-hosters.
- **Subsetting DejaVu Sans:** the font is read on the server and never sent to browsers, so subsetting saves only repo bytes. It needs a tool that isn't installed here (`pyftsubset`), and it would turn non-Latin version labels into boxes.
- **`opentype.js` 1.3.5 or 2.0.0:** both are 2026 releases from the 2.0 line, with little use yet. 1.3.4 is the proven one.

1. **The `POST /api/referrals` cross-site argument is wrong as written.** The design says "because it needs `application/json`, other sites can't make visitors' browsers send it without a CORS preflight".
