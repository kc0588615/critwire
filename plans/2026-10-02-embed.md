# Mission: critwire embed

This file is the mission's state. Agents: follow "In a mission session" in `~/.claude/CLAUDE.md`, and keep this file current.

## Brief


### Goal

A studio pastes one snippet into its own website and gets critwire's board and updates there, looking built-in. When this mission is done:

1. **Iframe widgets.** These are the one renderer; there's no shadow-DOM renderer. Build them from the existing portal components and the game's theme.
   - `/g/<game>/embed/board`: the public feedback items with vote counts, filterable by public stage and by type (bug or idea).
   - `/g/<game>/embed/updates`: the latest updates, each with its "From your feedback" items.
   - Opening an item or an update takes the player to its page on the portal.
   - The widgets use the host page's font by default (`font-family: inherit` through the loader), the game's colours, and a light, dark or auto mode. They contain no images.
2. **The loader `/embed/v1.js`.** Pasting one `<script>` tag creates the widget's iframe. It also:
   - Resizes the iframe to fit its content, through `postMessage`.
   - Passes the theme mode and `ref=embed`.
   - Offers a floating "Feedback" button variant that opens the board in an overlay.

   The loader must stay under 5 KB gzipped, set no cookies and never read the host page. It is a contract that must never break, so its URL is versioned and long-cached.
3. **Voting from the embed without extra vote power.**
   - The existing first-party vote cookie (`src/app/api/vote/route.ts`) stays the only record of a vote. Each browser gets one vote per item across the portal and every site that embeds it.
   - No partitioned cookie and no second vote cookie.
   - "Vote" in the embed opens critwire's own page in a popup, or a new tab where popups are blocked, and the vote is cast there. A third-party page must never be able to cast a vote without the player clicking on critwire's own interface.
   - After the vote, the embed shows the new count within the cache window. Showing "you voted" is best effort.
   - "Report a bug" and "Suggest an idea" open the portal's form. The embed contains no forms.
4. **Framing.** Embed routes send `frame-ancestors *`. Every other page keeps `'self'`, which the `reach` mission set up.
5. **Public JSON feeds.**
   - `/g/<game>/updates.json` (JSON Feed 1.1) and `/g/<game>/feedback.json`. The feedback feed lists the public items with their public stage, type, vote count, the version that shipped them and their URLs.
   - They are versioned, documented contracts. They answer GET requests from any origin (`Access-Control-Allow-Origin: *`) and never use credentials.
   - They contain public stages only, never internal statuses, emails or private reports.
6. **Caching.**
   - Embed routes and JSON feeds are cached for at most 5 minutes, and the hooks that already refresh the hub and the updates pages refresh them too.
   - A vote doesn't clear the cache on its own.
   - A held game or a suspended studio gives an empty, silent embed and a 404 from the JSON feeds.
   - `docs/deploy.md` documents the Cloudflare Cache Rule for embed and JSON routes.
7. **"Powered by Critwire"** appears in every embed on the hosted instance, with `ref=embed`, using the same rule as the portal footer. Self-hosted instances can turn it off.
8. **An "Embed" tab** in the "Put critwire on your site" panel from the `reach` mission. It has the snippet for each widget, a live preview, the theme choice and short instructions for each platform.

### Why

The owner expects the embed to become critwire's most important surface, because studios with their own website want the board inside it. Competitors (Canny, Nolt, Headway) embed through an iframe created by a small script, and so should critwire. The owner decided (2026-10-02) that embedding must not give anyone extra votes.

Read the review, `/srv/critter-ai/agent-state/missions/briefs/2026-10-02-integrations-review.md`. One part is overruled: its partitioned-cookie voting gave an extra vote per embedding site, which the owner rejected.

### Findings

Ranked by impact on this mission. Each "Fix" is what the target design does.

1. **One refresher serves both edits and votes, so the embed can't follow edits without also following votes.**
   - `revalidateGameLanding` (`src/hooks/revalidateGameLanding.ts:15-25`) has three callers: the issue hook (`src/collections/Issues/hooks/revalidateIssueLanding.ts:50-63`), the update hook (`src/collections/PatchNotes/hooks/revalidatePatchNotes.ts:35,38,50`) and every vote (`src/collections/IssueVotes/hooks/adjustUpvoteCount.ts:34`).
   - Adding the embeds and feeds there would break the Brief's "a vote doesn't clear the cache on its own". It breaks SRP: one function with two reasons to change.
   - **Fix:** two exports that share the slug lookup. `revalidateGameLanding` refreshes only the hub and is called by votes. `revalidateGameContent` refreshes the hub, both embeds and both feeds, and is called by edits.
2. **The issue hook's field gate misses "Shipped in", and a naive fix would break the kanban contract.**
   - `LANDING_FIELDS` (`revalidateIssueLanding.ts:17-27`) has no `fixedInPatchNote`. The board embed ("Shipped in v1.4") and `feedback.json` (`shipped_in`) both show it, so linking an item to an update wouldn't refresh them.
   - Adding the field to the `===` comparison (`:44`) would compare a relationship by reference. A populated object never equals another copy of itself, so every kanban drag would revalidate, which breaks the contract `tests/int/issue-revalidation` guards.
   - **Fix:** compare `fixedInPatchNote` by `extractID`, as `revalidateLinkedUpdates` already does.
3. **COOP lives in nginx, which E2E never runs, and on the vote page it cuts the popup off from the embed.**
   - `nginx.conf:42` sends `Cross-Origin-Opener-Policy: same-origin-allow-popups` on every response.
   - A popup opened from a cross-site iframe starts out `unsafe-none`, because its creator isn't same-origin with its own top-level page. When that popup lands on a `same-origin-allow-popups` page, the browser switches it to a new browsing context group. The popup's `window.opener` becomes null, and the embed's handle to it reads `closed === true` straight away.
   - The vote still works, but nothing can tell the embed about it. A "was the popup blocked?" check made after navigation would also misfire.
   - E2E serves `next start` without nginx, so it can't prove any of this. It's the same gap the `reach` mission closed for framing.
   - **Fix:**
     - The app owns COOP in `next.config.ts` `headers()` (`:52`): `same-origin-allow-popups` everywhere, and `unsafe-none` on feedback item pages only.
     - nginx drops its COOP line, and `tests/int/nginx-headers` forbids it.
4. **The portal layout can't host an embed.**
   - Every page under `src/app/(public)/g/[gameSlug]/` renders inside `PortalFrame` (`layout.tsx:23`): nav, footer, `ReferralPing` and `min-h-screen` (`src/components/game/PortalFrame.tsx:26`).
   - The `(public)` root layout adds the preloaded Atkinson body font (`(public)/layout.tsx:6,14`), and `globals.css:142` gives `body` a `min-h-[100vh]`.
   - An embed nested there would carry the chrome and download a font the widget must not use. Its content would always be at least the iframe's height, so the iframe could grow but never shrink.
   - **Fix:** a separate root route group, `src/app/(embed)/`, with its own `<html>`.
5. **The portal gate redirects, which is wrong inside a frame.**
   - `requirePortalProject` (`src/lib/game-portal/getGameProject.ts:54`) redirects held and suspended games to `/unavailable`. That page sends `frame-ancestors 'self'`, so on a studio's site the frame shows a browser error instead of the Brief's "empty, silent embed".
   - **Fix:** embed pages use `getGameProject` and render an empty document. The feeds answer 404, as `updates/feed.xml/route.ts:22` does. This isn't a bug today, but it's a rule to add to `docs/patterns.md`.
6. **Portal links prefetch.**
   - `UpdateEntry.tsx:29`, `FeedbackRow.tsx:16`, `FeedbackBoard.tsx:22,83` and `FeedbackActions.tsx:15,19` all use `next/link`. It prefetches links in the viewport and navigates in place.
   - In an embed that loads on every host page view, that means several extra origin requests per view, and navigation inside the frame.
   - **Fix:** the embed's rows and links are small components of their own, with plain `<a target="_blank">`. They reuse only the presentational pieces: `StatusMark`, `FeedbackTypeTag`, `VoteCount`, `formatDate` and `PUBLIC_STAGES`.
7. **Referral columns come from the share platforms, not from the accepted sources.**
   - `ReferralCounts.tsx:38` builds its columns from `SHARE_PLATFORMS`. `/api/referrals` accepts `REF_SOURCES` (`src/lib/share/platforms.ts:8`), whose comment already expects `embed`.
   - Adding `embed` would count arrivals that the Share tab never shows.
   - **Fix:** a label for every `RefSource` (`refSourceLabel`), with the columns built from `REF_SOURCES`.
8. **"Powered by" has no rule to share.**
   - `PortalFooter.tsx:40-43` always shows it, linking to `/`. The Brief wants the embed to follow the footer's rule, with an off switch for self-hosted instances.
   - **Fix:** `isPoweredByShown()` in `src/lib/hosting.ts`, used by both. It reads `CRITWIRE_HIDE_POWERED_BY`, which must be `1` or empty and is checked at boot like `CRITWIRE_OPEN_SIGNUP`.
9. **Sentry would meter every host page view.**
   - `src/instrumentation-client.ts:6` samples 10% of page loads as traces, and the browser SDK tracks a session per load by default.
   - Inside an embed, every view of a studio's site becomes Sentry traffic and uses Sentry quota.
   - **Fix:** in embed documents (path `/g/<game>/embed/`), report errors only: `tracesSampleRate: 0`, and the `BrowserSession` integration filtered out.
10. **Small DRY gaps the embed would otherwise widen:**
    - `withRef` is private to `src/lib/share/kit.ts:41`, and the embed tags every link `ref=embed`. Export it.
    - `shippedUpdate` and `updateName` (`FeedbackStatus.tsx:23,32`) are domain helpers in a component file, and `feedback.json` (a lib module) needs them. Move them to `src/lib/game-portal/shipped.ts`.
    - The "takes ideas" rule, `reportForm?.acceptIdeas !== false`, is written four times (`FeedbackActions.tsx:18`, `feedback/new/page.tsx:61,70`, `feedback/new/submit/route.ts:74`). The embed would add a fifth. Extract `acceptsIdeas(project)`.
    - `themeStyle` (`themeStyle.ts:69-78`) hard-codes the ten colour-variable names for a single palette, and the embed needs two palettes. Extract `paletteVars(colors, prefix)`.
    - The RSS item title (`updates/feed.xml/route.ts:35`) is also the JSON Feed item title. Extract `updateFeedTitle(note)`.
11. **The cross-origin E2E host is ad hoc, and the obvious replacement would test the wrong thing.**
    - `tests/e2e/framing.spec.ts:61-65` starts a one-off server inside a single test. The embed specs and the screenshots need one shared host-page server.
    - The host must be on `127.0.0.1`. `localhost:<other port>` would be same-site, because ports don't change the site. The iframe would then receive the `SameSite=Lax` vote cookie, and the voting tests would pass for the wrong reason.
    - `page.route` can't stand in either: Chromium's private-network check blocks it (`framing.spec.ts:57-60`).

**Fine as is, and reused unchanged:**
- the public read rules (`src/access/publicRead.ts:17-26`);
- `publicIssuesWhere`, `publicStage` and `PUBLIC_STAGES`;
- `queryPublishedPatchNotes`, `queryShippedFeedback` and `resolveProjectTheme`;
- the vote route's defences: JSON only (`src/app/api/vote/route.ts:34`), no CORS headers, a `SameSite=Lax` cookie (`:62-66`) and a hashed token;
- `portalPaths` as the only URL builder;
- the reach mission's rule that the last matching `headers()` entry wins.

**`src/app/(embed)/layout.tsx`** is a second root layout, with no `bodyFont` and no portal chrome. It renders:
- `<html lang="en" suppressHydrationWarning>`;
- `globals.css`, then `embed.css`;
- `NuqsAdapter`;
- `robots: noindex`;
- a `next/script` `beforeInteractive` boot script, `EMBED_BOOT_SCRIPT` from `src/lib/embed/boot.ts`. Before first paint it sets two things:

#### 2. The widgets

**Board:**
- **Data.** `queryPublicFeedback(projectID)` is new in `src/lib/game-portal/issues.ts`:
  - public, non-archived items (`publicIssuesWhere`);
  - sorted `-isPinned`, `-upvoteCount`, `-createdAt`;
  - the shipping update populated through `SHIPPED_IN_SELECT`;
  - read with `overrideAccess: false`;
  - at most `PUBLIC_FEEDBACK_FEED_LIMIT = 500` items.
- **One mapping for two outputs.** `feedbackFeed()` maps the items once, and the same objects feed both `EmbedBoard` and `feedback.json`. So the widget can never show more than the feed, and the feed never more than the portal.
- **Filters (`EmbedBoard`, client).**
  - A stage filter (All plus the four public stages, each with its count) and a type filter (All, Bugs and, when `acceptsIdeas`, Ideas).
  - Both are `aria-pressed` buttons, never a `<form>`.
  - State uses nuqs `useQueryStates({ stage, type })` with the existing parsers from `feedbackSearchParams`, and `history: 'replace'`. A `pushState` inside an iframe would add entries to the host page's back button.
  - The filters and list sit in `<Suspense fallback={null}>`, because the page is ISR (the same pattern as `WelcomePanel`).
- **Rows.**
  - The board shows the first `EMBED_ROWS = 10` matching items, then "See all N", which goes to the portal's list through `feedbackHref(paths.feedback, { stage, type })`.
  - Each row has a vote link (`VoteCount` inline), the title linking to the item page, the stage (`StatusMark` and its label, or "Shipped in <version>") and the type tag.
- **Header.** "Report a bug", and "Suggest an idea" when `acceptsIdeas`, both linking to `portalPaths.newFeedback(type)`. They sit outside the Suspense boundary.
- **Links.** Every link has `target="_blank" rel="noopener"` and goes through `withRef(url, 'embed')`.

**Updates** (`EmbedUpdates`, a server component with no client state):
- The newest `LATEST_UPDATES_LIMIT` updates, the hub's 3, now exported from `LatestUpdates.tsx`, through `queryPublishedPatchNotes`.
- Each shows its version, date, title link and summary, and "From your feedback" through `queryShippedFeedback`: each item's title link, type and votes.
- Then "All updates" and "RSS".

**Empty states:** "No feedback yet" with the two form links, and "No updates yet".

**No images and no font files:**
- Nothing in the embed tree renders an image or imports `next/font`.
- `embed.css` sets `--fs-font-display` to the host font.
- So the widget downloads no image and no font file.

**Theme modes:**
- **`embedPalettes(colors)`** returns `{ light, dark }`.
  - The game's own palette is used as-is for its own scheme. It counts as dark when `relativeLuminance(background) < 0.18`.
  - The other scheme is a fixed neutral palette carrying the game's accent pair, provided that accent has at least 3:1 contrast against the neutral background.
  - Failing that, it uses the swapped pair: `accentForeground` becomes the fill. The theme schema already guarantees 4.5:1 between the two.
  - Failing both, it uses the neutral palette's own accent.
  - The result is parsed with `siteThemeColorsSchema`, so a bad constant throws at once.
- **`embedStyle(theme)`** returns `paletteVars(light, '--cw-light')`, `paletteVars(dark, '--cw-dark')` and the radius tokens from `themeStyle`.
- **`embed.css`** maps the `--fs-*` variables:
  - to the light set on `.cw-embed`;
  - to the dark set under `:root[data-mode=dark]`, and under `@media (prefers-color-scheme: dark) { :root[data-mode=auto] }`;
  - with `color-scheme` set to match.
  - One cached HTML page per widget therefore serves every mode.
- **Font and body:**
  - `.cw-embed` gets `font-family: var(--cw-font, system-ui, sans-serif)`, overriding `portal.css:33`.
  - `body` gets `min-height: 0` and a transparent background.

#### 3. The loader, `/embed/v1.js` (contract v1)

```html
<script src="https://<instance>/embed/v1.js" data-game="<slug>" data-widget="board" data-theme="auto" async></script>
```

**Attributes:**
- `data-game` is required.
- `data-widget` is `board` (the default), `updates` or `button`.
- `data-theme` is `auto` (the default), `light` or `dark`.
- `data-stage` and `data-type` set the board's initial filter.
- Values are passed through unchecked; the embed's parsers ignore unknown ones.

**What the loader does.** Everything runs inside one IIFE, with no globals.

1. **Find itself.**
   - It reads `s = document.currentScript`.
   - With no script or no `data-game`, it calls `console.error` and stops: fail loud, but never break the host page.
   - It takes `origin = new URL(s.src).origin`.
2. **Inline widgets (board and updates).**
   - It creates an `<iframe>`: a title, `loading="lazy"`, `width: 100%`, `border: 0`, and a height of 400px until the first resize message.
   - It inserts the iframe right after `s`.
   - It reads `getComputedStyle(iframe).fontFamily`. That is what `font-family: inherit` resolves to on the loader's own element.
   - Only then does it set `src` to `origin/g/<game>/embed/<widget>?theme=…[&stage=…][&type=…]#font=<encoded>`.
   - The font travels in the URL fragment, so it never reaches the server, a log or a cache key.
3. **The floating button.**
   - A fixed `<button type="button">Feedback</button>` in the bottom-right corner, with `font: inherit`.
   - Its colours are neutral, light or dark by `data-theme`; `auto` follows the visitor's setting through `matchMedia`.
   - A click creates, the first time, a `<dialog aria-label="Feedback">` holding a Close button and the board iframe at `height: min(80vh, 720px)`, then calls `showModal()`.
   - The native dialog traps focus, closes on Escape and returns focus to the button.
4. **Messages.** One `message` listener, which accepts a message only when all three hold: `e.source === iframe.contentWindow`, `e.origin === origin` and `e.data?.critwire === 1`.
   - `resize` sets the iframe's height to `ceil(height)`, clamped to 0–20000 px. It applies to inline iframes only.
   - `close` calls `dialog.close()`.
5. **What it never does:**
   - set or read cookies, or touch storage;
   - make network requests of its own;
   - read `document.title`, `location` or any other part of the DOM;
   - leave globals behind.

**Protocol v1** (`src/lib/embed/protocol.ts`, documented in `docs/embed.md`):

| From → to | Message | `postMessage` target |
|---|---|---|
| embed → loader | `{ critwire: 1, type: 'resize', height }`, on every size change of `.cw-embed` | `'*'`; it carries only a height |
| embed → loader | `{ critwire: 1, type: 'close' }`, on Escape | `'*'` |
| vote page → embed | `{ critwire: 1, type: 'vote', issueId, votes, voted }`, after a successful vote or withdrawal | the page's own origin, so only a critwire-origin opener receives it |

**Versioning:**
- `v1.js` and protocol 1 may only gain optional attributes and new message types.
- Anything incompatible becomes `/embed/v2.js`, and embed pages keep answering v1 for good.
- The file opens with a comment saying so.
- The 5 KB gzipped budget is enforced by a test (section 12).

#### 4. Voting from the embed

**The flow:**
1. **The vote link.** Each row's vote control is `<a href="<item page>?ref=embed" target="_blank">▲ 12</a>`.
   - Its click handler calls `window.open(href, 'critwire-vote', 'popup,width=480,height=640')`.
   - If that returns a window, the handler calls `preventDefault()` and keeps the reference.
   - If it returns `null` (the popup was blocked), the link's default action opens a new tab instead.
2. **The page that opens.** It's the existing item page, `/g/<game>/feedback/<slug>`, a first-party page, so the one `cw_vote_token` cookie applies.
   - If the player already voted on the portal, the page shows "Upvoted" and the count already includes them.
   - So each browser has one vote per item across the portal and every site that embeds it, with no new cookie.
3. **The vote.** The player clicks "Upvote" (`VoteButton`; its call to the route doesn't change). On success, `VoteButton` also calls `notifyOpener()`, which posts `{ critwire: 1, type: 'vote', issueId, votes, voted }` to `window.opener`, if there is one, with the target origin `location.origin`.
4. **The best-effort part.**
   - The embed accepts the message only from its own origin and only from the window it opened. It then shows the new count and "Voted" on that row.
   - This works whenever the opener survives: the popup was allowed, and the host page has no strict COOP of its own.
   - It applies only to that page view.
5. **After a reload,** the embed shows the cached count until its cache window ends. The vote hooks still refresh only the hub and the shipped update's page (Finding 1).

**COOP.** The app sends `same-origin-allow-popups` on every route except feedback item pages, which send `unsafe-none` so the popup keeps its opener.
- Item pages hold nothing private: public text, plus the player's own vote state, which a cross-origin opener can't read.
- They have no message listener, and other sites still can't frame them.
- Every other page, the admin included, keeps `same-origin-allow-popups`.
- Without the exception, voting still works; only step 4 is lost.

**Why a third-party page can't cast a vote without a click on critwire's own interface:**
- **The embed can't vote.** It contains no `VoteButton` and never calls `/api/vote`. Inside a third-party frame the `SameSite=Lax` cookie isn't sent, so it couldn't vote as the player anyway.
- **The host page can't call the API.**
  - `/api/vote` takes only `application/json` (`route.ts:34`) and sends no CORS headers, so a cross-site JSON `fetch` fails its preflight.
  - Forms and `no-cors` requests get a 400 before the body is read.
  - The Lax cookie isn't sent on cross-site POSTs either.
- **The vote page can't be framed** (`frame-ancestors 'self'`), so it can't be overlaid or clickjacked. The only framable routes are the two widgets, and they hold no vote control, only links that open critwire's page.
- **An opener can't click for the player.** A page that opens the item page itself can navigate it, or post messages it never reads. It can't send trusted clicks into another origin's window, and `notifyOpener` posts only to critwire's own origin.

#### 5. Headers

`next.config.ts` `headers()` entries, in order. The last match wins for each header name.

```ts
{ source: '/:path*', headers: [
    { key: 'Content-Security-Policy', value: "frame-ancestors 'self'" },
    { key: 'Cross-Origin-Opener-Policy', value: 'same-origin-allow-popups' } ] },
// The two widgets: any site may frame them.
{ source: '/g/:game/embed/:widget', headers: [{ key: 'Content-Security-Policy', value: 'frame-ancestors *' }] },
// Feedback item pages (not the form at /feedback/new) keep their opener, so the embed's vote popup can report back.
{ source: '/g/:game/feedback/:slug((?!new$)[^/]+)', headers: [{ key: 'Cross-Origin-Opener-Policy', value: 'unsafe-none' }] },
// The loader is a contract: cached for a day, at the edge and in browsers.
{ source: '/embed/v1.js', headers: [{ key: 'Cache-Control', value: 'public, max-age=86400, s-maxage=86400' }] },
```

- **The loader's caching works without a route handler.** Next's static-file handler and `send` set `Cache-Control` only when it's absent, so this entry holds for a file in `public/`. The E2E suite checks it.

#### 6. The JSON feeds

**Both feeds:**
- **Missing games.** `getGameProject(slug)` returning null (an unknown, held or suspended game) gives `404 {"error":"Not found."}`.
- **Headers.** Every answer, 404s included, goes through `feedResponse`:
  - `Access-Control-Allow-Origin: *`;
  - never `Access-Control-Allow-Credentials`;
  - no cookies read (ISR couldn't read them anyway).
- **Methods.** GET only, with no preflight handling. Simple GETs need none.

**`updates.json`** is JSON Feed 1.1, served as `application/feed+json; charset=utf-8`. It lists the 20 newest published updates, as RSS does:

```json
{ "version": "https://jsonfeed.org/version/1.1",
  "title": "<Game> — Updates", "home_page_url": "<site>/g/<slug>/updates",
  "feed_url": "<site>/g/<slug>/updates.json", "description": "The latest updates for <Game>.", "language": "en",
  "items": [{ "id": "42", "url": "<site>/g/<slug>/updates/<slug>", "title": "v1.4 — Harbor hotfix",
              "summary": "…", "content_text": "<the summary, or the title>", "date_published": "2026-…Z" }] }
```

- `id` is the update's database ID, so it survives a slug change.
- `summary` is left out when empty.

**`feedback.json`** is contract v1, served as `application/json; charset=utf-8`:

```json
{ "version": 1, "title": "<Game> feedback", "home_page_url": "<site>/g/<slug>/feedback",
  "feed_url": "<site>/g/<slug>/feedback.json",
  "items": [{ "id": "123", "url": "<site>/g/<slug>/feedback/<slug>", "title": "…", "summary": null,
              "type": "bug", "stage": "under-review", "votes": 12, "date_created": "2026-…Z",
              "shipped_in": { "version": "v1.4", "title": "…", "url": "<site>/g/<slug>/updates/<slug>" } }] }
```

- **Values:**
  - `type` is `bug` or `idea`.
  - `stage` is `under-review`, `planned`, `in-progress` or `shipped`, from `publicStage()`.
  - `shipped_in` is null, or a published update, from `shippedUpdate()`; its `version` may be null.
  - Every item has every key, with null when empty, so consumers never have to test whether a key is present.
- **Contents:**
  - Only public, non-archived items, at most 500, pinned first, then by votes, then newest.
  - Never `status`, the category, the studio's notes, report data or emails.
- **Stability:** fields may be added, but never removed, renamed or retyped. Anything incompatible gets a new URL (`feedback.v2.json`).

#### 7. Caching and refresh

- **Server.**
  - All four routes are ISR with `revalidate = 300`, so Next sends `s-maxage=300`.
  - Neither the embed HTML nor the feeds vary by query string: the embed reads its query and fragment in the browser.
  - So each game has one cache entry per route.
- **On-demand refresh**, in `src/hooks/revalidateGameLanding.ts`:
  - `revalidateGameContent(gameProject, payload)` calls `revalidatePath` on the game's hub, both embeds and both feeds.
    - The issue and update hooks call it wherever they call `revalidateGameLanding` today.
    - The issue gate adds `fixedInPatchNote`, compared by ID. It already covers `summary`.
  - `revalidateGameLanding` refreshes only the hub, and only `adjustUpvoteCount` calls it. **A vote never touches the embeds or the feeds.**
  - `revalidateGamePortal`, which runs on game edits, holds, renames and suspensions, adds `revalidatePath(EMBED_ROUTE, 'layout')`. The feeds already sit under `PORTAL_ROUTE`.
- **Held or suspended.**
  - The game hook, or `revalidateSuspension`, refreshes everything.
  - The embed renders empty and posts `height: 0`, so the iframe collapses.
  - Both feeds answer 404.
- **Edge (`docs/deploy.md`).** Add a Cloudflare Cache Rule for `(starts_with(http.request.uri.path, "/g/") and (http.request.uri.path contains "/embed/" or ends_with(http.request.uri.path, ".json")))`:
  - eligible for cache;
  - Edge TTL "Ignore cache-control header and use this TTL: 5 minutes", so Next's one-year `stale-while-revalidate` never reaches the edge;
  - Browser TTL: respect the origin.
  - Cloudflare's defaults already cache the loader (a `.js` file).
  - Everything else under `/g/` stays out of the edge cache, as it is today.
- **What "5 minutes" means in practice.**
  - After a quiet period, ISR serves the stale page once while it renders a fresh one, so the first view can show an older count.
  - Edits, holds and suspensions don't wait for that; they refresh on demand. Only vote counts do.
  - `docs/embed.md` says so.

### Rejected alternatives

- **Embed pages inside the portal tree, with the portal moved into a `(portal)` group.** It moves every portal file, changes `UPDATES_ROUTE`, and still inherits the preloaded body font from `(public)/layout.tsx`.
- **Dynamic embed pages with HTTP caching only, as the badge does.** Next overwrites `Cache-Control` on pages, and without Cloudflare every host page view would query Postgres.
- **Theme, filters or font as query parameters the server reads.** Each value would be its own ISR entry, and the font would reach the server.
- **A `data-font` attribute instead of the inherited font.** The studio would have to type it, and the Brief asks for inheritance.
- **Sending the font by `postMessage` after load.** The fallback font would flash, and the widget would resize a second time.
- **A dedicated vote page for the popup.** It's a second URL for the same item, for a COOP exception that's just as safe on the item page.
- **Keeping COOP on item pages too.** Voting works, but "Voted" and the new count could never reach the embed. No channel survives the switch of browsing context group, because storage and `BroadcastChannel` are partitioned by top-level site.
- **Polling the vote count, or a nonce channel through the server.** New endpoints and requests for a best-effort label.
- **The loader adding `ref=embed` to the iframe URL.** The ISR page ignores query strings, so it would do nothing. The embed tags its own links instead, which also covers the bare iframe.
- **A route handler for `/embed/v1.js`.** More code for headers that `headers()` already sets on a static file.
- **`localhost:<other port>` or `page.route` as the E2E host.** The first is same-site, so the Lax cookie would reach the frame. Chromium's private-network check blocks the second.

### Risks and conservative choices

- **The COOP exception on item pages is the one security-header change.**
  - It's scoped to item pages, which hold nothing private and can't be framed. Every other page keeps `same-origin-allow-popups`.
  - Reverting it means deleting one `headers()` entry; the embed then shows new counts only after the cache window.
- **The font is the one thing the loader reads:** the inherited `font-family` of its own iframe. If the owner reads "never read the host page" more strictly, delete that one line and the widget falls back to `system-ui`.
- **Host web fonts don't reach the iframe.** Only system font stacks match exactly. Documented.
- **Sandboxed host frames without `allow-popups`,** which some site builders use, can't open the vote popup or the portal links. Documented per platform; untried platforms say "should work".
- **Counts can be stale after a quiet period,** because ISR serves one stale view while it refreshes. Edits, holds and suspensions refresh on demand.
- **`prebuild` runs vitest inside the Docker builder,** where devDependencies are installed. It can't be checked on this VPS, which has no Docker. The test file runs in Node only.
- **Cloudflare's own cookies** (`__cf_bm`, under Bot Fight Mode) would appear in embeds. The app sets none. Documented.
- **Traffic cost without a Cache Rule** (self-hosted instances): each host page view costs one ISR hit, served from memory, with no database query.
- **Double-click tricks,** where a page opens the popup under the player's cursor, still need the player's real click on critwire's page. The prize is one vote per browser, as it already is.

**Candidate handoff items.** The lead decides whether to file them.

1. **Decision, with a default:** the item page doesn't send COOP `same-origin-allow-popups`, so the embed can show "Voted" and the new count straight away. The alternative is COOP on every page, with the embed's count updating within 5 minutes. Default: keep the exception, which can be reverted with one line.
2. **Before the production deploy (it blocks nothing now):**
   - add the Cloudflare Cache Rule from `docs/deploy.md` on the production zone;
   - check that Bot Fight Mode's `__cf_bm` cookie isn't set on `/g/*/embed/*`.

VERDICT: APPROVE_WITH_CHANGES

Checked every cited line. Tenant scoping and access control reuse `publicIssuesWhere` and `overrideAccess: false` throughout. No over-engineering beyond the goal; the `prebuild` size test is required by the Brief.

MUST-FIX:
1. **The board ships every item's `summary` to the browser.** Section 2 says "the same objects feed both `EmbedBoard` and `feedback.json`", and `EmbedBoard` is a client component. `summary` is an unbounded `textarea` (`src/collections/Issues/index.ts:64`), the board never renders it, and the limit is 500 items, so the embed's RSC payload could carry hundreds of KB of player text on every host page view, for the surface the owner expects to be the most important. ## Architecture review (Astra)

VERDICT: APPROVE_WITH_CHANGES

MUST-FIX:

1. **The cache architecture does not meet the freshness contract.** Section 7 invalidates Next’s cache but never Cloudflare’s. Edits and suspensions can therefore remain visible at the edge; an expired edge entry can also cache a stale ISR response for another five minutes. Define coordinated invalidation and an end-to-end freshness bound, or remove the second cache layer. Verify this through a caching proxy, not only `next start`. [Next.js CDN guidance](https://nextjs.org/docs/app/guides/cdn-caching)
2. **Filtering after the global 500-item cutoff produces incorrect results.** A stage or type can appear empty despite having public items, and “See all N” reports a truncated count. Fetch bounded results per filter with authoritative counts, or explicitly present the widget as a limited sample without claiming complete counts.

SHOULD-CONSIDER:

1. Pass the client board only fields it renders; serializing up to 500 unused, unbounded summaries unnecessarily enlarges every embed.
2. Specify HTML/RSC cache separation before adopting the earlier review’s suggestion to ignore query strings; Next uses `_rsc` to distinguish response variants. [Next.js CDN guidance](https://nextjs.org/docs/app/guides/cdn-caching)
3. Bound “From your feedback” results per update, with a link to the full update. Reusing the currently unbounded query makes widget size grow with a game’s history.
