# Mission: critwire embed

This file is the mission's state. Agents: follow "In a mission session" in `~/.claude/CLAUDE.md`, and keep this file current.

## Brief


### Goal

A studio pastes one snippet into its own website and gets critwire's board and updates there, looking built-in. When this mission is done:

1. **Iframe widgets.** These are the one renderer; there's no shadow-DOM renderer. Build them from the existing portal components and the game's theme.
   - `/g/<game>/embed/board`: the public feedback items with vote counts, filterable by public stage and by type (bug or idea).
   - `/g/<game>/embed/updates`: the latest updates, each with its "From your feedback" items.
   - Opening an item or an update takes the player to its page on the portal.
   - The widgets use the host page's font by default (`font-family: inherit` through the loader), the game's colours, and a light, dark or auto mode. They contain no images.
2. **The loader `/embed/v1.js`.** Pasting one `<script>` tag creates the widget's iframe. It also:
   - Resizes the iframe to fit its content, through `postMessage`.
   - Passes the theme mode and `ref=embed`.
   - Offers a floating "Feedback" button variant that opens the board in an overlay.

   The loader must stay under 5 KB gzipped, set no cookies and never read the host page. It is a contract that must never break, so its URL is versioned and long-cached.
3. **Voting from the embed without extra vote power.**
   - The existing first-party vote cookie (`src/app/api/vote/route.ts`) stays the only record of a vote. Each browser gets one vote per item across the portal and every site that embeds it.
   - No partitioned cookie and no second vote cookie.
   - "Vote" in the embed opens critwire's own page in a popup, or a new tab where popups are blocked, and the vote is cast there. A third-party page must never be able to cast a vote without the player clicking on critwire's own interface.
   - After the vote, the embed shows the new count within the cache window. Showing "you voted" is best effort.
   - "Report a bug" and "Suggest an idea" open the portal's form. The embed contains no forms.
4. **Framing.** Embed routes send `frame-ancestors *`. Every other page keeps `'self'`, which the `reach` mission set up.
5. **Public JSON feeds.**
   - `/g/<game>/updates.json` (JSON Feed 1.1) and `/g/<game>/feedback.json`. The feedback feed lists the public items with their public stage, type, vote count, the version that shipped them and their URLs.
   - They are versioned, documented contracts. They answer GET requests from any origin (`Access-Control-Allow-Origin: *`) and never use credentials.
   - They contain public stages only, never internal statuses, emails or private reports.
6. **Caching.**
   - Embed routes and JSON feeds are cached for at most 5 minutes, and the hooks that already refresh the hub and the updates pages refresh them too.
   - A vote doesn't clear the cache on its own.
   - A held game or a suspended studio gives an empty, silent embed and a 404 from the JSON feeds.
   - `docs/deploy.md` documents the Cloudflare Cache Rule for embed and JSON routes.
7. **"Powered by Critwire"** appears in every embed on the hosted instance, with `ref=embed`, using the same rule as the portal footer. Self-hosted instances can turn it off.
8. **An "Embed" tab** in the "Put critwire on your site" panel from the `reach` mission. It has the snippet for each widget, a live preview, the theme choice and short instructions for each platform.

### Why

The owner expects the embed to become critwire's most important surface, because studios with their own website want the board inside it. Competitors (Canny, Nolt, Headway) embed through an iframe created by a small script, and so should critwire. The owner decided (2026-10-02) that embedding must not give anyone extra votes.

Read the review, `/srv/critter-ai/agent-state/missions/briefs/2026-10-02-integrations-review.md`. One part is overruled: its partitioned-cookie voting gave an extra vote per embedding site, which the owner rejected.

### Findings

Ranked by impact on this mission. Each "Fix" is what the target design does.

1. **Next's ISR can't bound staleness behind a second cache, so the embeds and feeds can't use it.**
   - An ISR entry older than its `revalidate` window is served once more while it re-renders, even after `revalidatePath`. The time check runs first and skips the tag check (`node_modules/next/dist/server/lib/incremental-cache/index.js:405-418`, Next 16.2.6).
   - Only pages turn an expired tag into a blocking render (`next/dist/build/templates/app-page.js:654`). Route handlers always serve one stale response after `revalidatePath` (`next/dist/server/response-cache/index.js:198-203`).
   - After a quiet stretch, that one response can be hours old: a held game's content, or old counts. A Cloudflare entry in front keeps it for its whole TTL, and the hooks can't reach Cloudflare without a purge token.
   - So "ISR refreshed by the hooks, behind the edge" has no honest bound.
   - **Fix:** the embeds and feeds keep no server cache. They render per request and send one explicit HTTP cache header whose TTLs add up to 5 minutes (section 7). It's the badge's model (`src/lib/share/badge.ts:11-16`).
   - Noted, out of scope: the hub and the RSS feed have the same one-response window after a quiet stretch, a hold included. No HTML is edge-cached today, so it's one response, not a TTL.
2. **COOP lives in nginx, which E2E never runs, and on the vote page it cuts the popup off from the embed.**
   - `nginx.conf:42` sends `Cross-Origin-Opener-Policy: same-origin-allow-popups` on every response.
   - A popup opened from a cross-site iframe starts out `unsafe-none`, because its creator isn't same-origin with its own top-level page. When that popup lands on a `same-origin-allow-popups` page, the browser switches it to a new browsing context group. The popup's `window.opener` becomes null, and the embed's handle to it reads `closed === true` straight away.
   - The vote still works, but nothing can tell the embed about it. A "was the popup blocked?" check made after navigation would also misfire.
   - E2E serves `next start` without nginx, so it can't prove any of this. It's the same gap the `reach` mission closed for framing.
   - **Fix:**
     - The app owns COOP in `next.config.ts` `headers()` (`:52`): `same-origin-allow-popups` everywhere, and `unsafe-none` on feedback item pages only.
     - nginx drops its COOP line, and `tests/int/nginx-headers` forbids it.
3. **The portal layout can't host an embed.**
   - Every page under `src/app/(public)/g/[gameSlug]/` renders inside `PortalFrame` (`layout.tsx:23`): nav, footer, `ReferralPing` and `min-h-screen` (`src/components/game/PortalFrame.tsx:26`).
   - The `(public)` root layout adds the preloaded Atkinson body font (`(public)/layout.tsx:6,14`), and `globals.css:142` gives `body` a `min-h-[100vh]`.
   - An embed nested there would carry the chrome and download a font the widget must not use. Its content would always be at least the iframe's height, so the iframe could grow but never shrink.
   - **Fix:** a separate root route group, `src/app/(embed)/`, with its own `<html>`.
4. **The portal gate redirects, which is wrong inside a frame.**
   - `requirePortalProject` (`src/lib/game-portal/getGameProject.ts:54`) redirects held and suspended games to `/unavailable`. That page sends `frame-ancestors 'self'`, so on a studio's site the frame shows a browser error instead of the Brief's "empty, silent embed".
   - **Fix:** embed pages use `getGameProject` and render an empty document. The feeds answer 404, as `updates/feed.xml/route.ts:22` does. This isn't a bug today, but it's a rule to add to `docs/patterns.md`.
5. **Portal links prefetch.**
   - `UpdateEntry.tsx:29`, `FeedbackRow.tsx:16`, `FeedbackBoard.tsx:22,83` and `FeedbackActions.tsx:15,19` all use `next/link`. It prefetches links in the viewport and navigates in place.
   - In an embed that loads on every host page view, that means several extra origin requests per view, and navigation inside the frame.
   - **Fix:** the embed's rows and links are small components of their own, with plain `<a target="_blank">`. They reuse only the presentational pieces: `StatusMark`, `FeedbackTypeTag`, `VoteCount`, `formatDate` and `PUBLIC_STAGES`.
6. **Referral columns come from the share platforms, not from the accepted sources.**
   - `ReferralCounts.tsx:38` builds its columns from `SHARE_PLATFORMS`. `/api/referrals` accepts `REF_SOURCES` (`src/lib/share/platforms.ts:8`), whose comment already expects `embed`.
   - Adding `embed` would count arrivals that the Share tab never shows.
   - **Fix:** a label for every `RefSource` (`refSourceLabel`), with the columns built from `REF_SOURCES`.
7. **"Powered by" has no rule to share.**
   - `PortalFooter.tsx:40-43` always shows it, linking to `/`. The Brief wants the embed to follow the footer's rule, always on the hosted instance, with an off switch for self-hosted instances.
   - **Fix:** `isPoweredByShown()` in `src/lib/hosting.ts`, used by both (section 8).
8. **Sentry would meter every host page view.**
   - `src/instrumentation-client.ts:6` samples 10% of page loads as traces, and the browser SDK tracks a session per load by default.
   - Inside an embed, every view of a studio's site becomes Sentry traffic and uses Sentry quota.
   - **Fix:** in embed documents (path `/g/<game>/embed/`), report errors only: `tracesSampleRate: 0`, and the `BrowserSession` integration filtered out.
9. **Small DRY gaps the embed would otherwise widen:**
   - `withRef` is private to `src/lib/share/kit.ts:41`, and the embed tags every link `ref=embed`. Export it.
   - `shippedUpdate` and `updateName` (`FeedbackStatus.tsx:23,32`) are domain helpers in a component file, and `feedback.json` (a lib module) needs them. Move them to `src/lib/game-portal/shipped.ts`.
   - `LATEST_UPDATES_LIMIT` is private to a component (`LatestUpdates.tsx:12`), and the updates widget needs it. Move it to `src/lib/game-portal/patchNotes.ts`, beside `queryPublishedPatchNotes`.
   - The ranked order `['-isPinned', '-upvoteCount', '-createdAt']` is written three times (`src/lib/game-portal/issues.ts:88,136,160`), and the feed would add a fourth. Extract `RANKED_SORT`.
   - The "takes ideas" rule, `reportForm?.acceptIdeas !== false`, is written four times (`FeedbackActions.tsx:18`, `feedback/new/page.tsx:61,70`, `feedback/new/submit/route.ts:74`). The embed would add a fifth. Extract `acceptsIdeas(project)`.
   - `themeStyle` (`themeStyle.ts:69-78`) hard-codes the ten colour-variable names for a single palette, and the embed needs two palettes. Extract `paletteVars(colors, prefix)`.
   - The RSS item title (`updates/feed.xml/route.ts:35`) is also the JSON Feed item title. Extract `updateFeedTitle(note)`.
10. **The cross-origin E2E host is ad hoc, and the obvious replacement would test the wrong thing.**
    - `tests/e2e/framing.spec.ts:61-65` starts a one-off server inside a single test. The embed specs and the screenshots need one shared host-page server.
    - The host must be on `127.0.0.1`. `localhost:<other port>` would be same-site, because ports don't change the site. The iframe would then receive the `SameSite=Lax` vote cookie, and the voting tests would pass for the wrong reason.
    - `page.route` can't stand in either: Chromium's private-network check blocks it (`framing.spec.ts:57-60`).

**Fine as is, and reused unchanged:**
- the public read rules (`src/access/publicRead.ts:17-26`);
- `publicIssuesWhere`, `publicStage` and `PUBLIC_STAGES`;
- the portal board's one query per column, whose `totalDocs` is the true count (`FeedbackBoard.tsx:37`);
- `queryPublishedPatchNotes`, `queryShippedFeedback` and `resolveProjectTheme`;
- the revalidation hooks: they keep refreshing the hub and the updates pages, and the embeds and feeds need none (section 7);
- the vote route's defences: JSON only (`src/app/api/vote/route.ts:34`), no CORS headers, a `SameSite=Lax` cookie (`:62-66`) and a hashed token;
- `portalPaths` as the only URL builder;
- the reach mission's rule that the last matching `headers()` entry wins.

#### 2. The widgets

**Board:**
- **Data: one query per view.** The widget offers 15 views: All or one of the four public stages, times All, Bugs or Ideas.
  - The page runs `queryBoardColumn` once per view, in parallel, with `limit: EMBED_ROWS` (10).
  - Each result's `totalDocs` is the view's true count, as each column of the portal board already is.
  - `queryBoardColumn` gains `stage: null`, meaning every public stage (`publicIssuesWhere` already supports it), and a `limit` that defaults to `BOARD_COLUMN_LIMIT`. Its `select` stays as it is, with no `summary`.
  - So no stage looks empty when it isn't, and every count equals what the portal list shows for the same filter.
- **What reaches the browser.** Each view is `{ stage, type, total, rows }`, and each row an `EmbedFeedbackRow`.
  - `feedbackRow(issue)` builds each row as a new object with exactly those seven keys. The `Pick` type alone wouldn't stop extra fields (TypeScript accepts them), so the function builds the object, and E1 checks that the board's HTML holds no summary.
  - `feedbackFeedItem(issue)` spreads `feedbackRow(issue)` and adds `summary` and `date_created`. One mapping serves both outputs, so a row can never carry a field the feed doesn't have.
  - The worst case is 15 views of 10 rows of seven short fields: a few KB gzipped.
- **Filters (`EmbedBoard`, client).**
  - A stage filter (All plus the four public stages, each with its view's count for the current type) and a type filter (All, Bugs and, when `acceptsIdeas`, Ideas).
  - Both are `aria-pressed` buttons, never a `<form>`.
  - The state is local React state. The page parses the initial `?stage=&type=` with `createLoader(feedbackSearchParams)`, the list page's own parser, and passes it as props.
  - The page is dynamic, so the server renders the initial view's rows. There's no Suspense boundary, no empty first paint, and the iframe resizes once.
  - Switching filters only picks another view: no request and no URL change, so nothing reaches the host page's history.
- **Rows.**
  - The board shows the view's rows (at most 10). When `total` is higher, "See all N" goes to the portal's list through `feedbackHref(paths.feedback, { stage, type })`. That list uses the same `publicIssuesWhere`, so it shows N items.
  - Each row has a vote link (`VoteCount` inline), the title linking to the item page, the stage (`StatusMark` and its label, or "Shipped in <version>") and the type tag.
- **Header.** "Report a bug", and "Suggest an idea" when `acceptsIdeas`, both linking to `portalPaths.newFeedback(type)`.
- **Links.** Every link has `target="_blank" rel="noopener"` and goes through `withRef(url, 'embed')`.

**Updates** (`EmbedUpdates`, a server component with no client state):
- The newest `LATEST_UPDATES_LIMIT` updates (3, the hub's number, now in `patchNotes.ts`), through `queryPublishedPatchNotes`.
- Each shows its version, date, title link and summary.
- Then "From your feedback", bounded so the widget doesn't grow with a game's history:
  - `queryShippedFeedback` gains an optional `limit`, as `queryTopFeedback` already uses with `pagination: false`;
  - the widget asks for `EMBED_SHIPPED_LIMIT + 1` (6) and shows at most 5, each with its title link, type and votes;
  - when a sixth comes back, the list ends with "More in this update", linking to the update page.
- Then "All updates" and "RSS".

**Empty states:** "No feedback yet" with the two form links, and "No updates yet".

**No images and no font files:**
- Nothing in the embed tree renders an image or imports `next/font`.
- `embed.css` sets `--fs-font-display` to the host font.
- So the widget downloads no image and no font file.

**Theme modes:**
- **`embedPalettes(colors)`** returns `{ light, dark }`.
  - The game's own palette is used as-is for its own scheme. It counts as dark when `relativeLuminance(background) < 0.18`.
  - The other scheme is a fixed neutral palette carrying the game's accent pair, provided that accent has at least 3:1 contrast against the neutral background.
  - Failing that, it uses the swapped pair: `accentForeground` becomes the fill. The theme schema already guarantees 4.5:1 between the two.
  - Failing both, it uses the neutral palette's own accent.
  - The result is parsed with `siteThemeColorsSchema`, so a bad constant throws at once.
- **`embedStyle(theme)`** returns `paletteVars(light, '--cw-light')`, `paletteVars(dark, '--cw-dark')` and the radius tokens from `themeStyle`.
- **`embed.css`** maps the `--fs-*` variables:
  - to the light set on `.cw-embed`;
  - to the dark set under `:root[data-mode=dark]`, and under `@media (prefers-color-scheme: dark) { :root[data-mode=auto] }`;
  - with `color-scheme` set to match.
  - One HTML response per widget URL therefore serves every visitor's mode.
- **Font and body:**
  - `.cw-embed` gets `font-family: var(--cw-font, system-ui, sans-serif)`, overriding `portal.css:33`.
  - `body` gets `min-height: 0` and a transparent background.

#### 3. The loader, `/embed/v1.js` (contract v1)

```html
<script src="https://<instance>/embed/v1.js" data-game="<slug>" data-widget="board" data-theme="auto" async></script>
```

**Attributes:**
- `data-game` is required.
- `data-widget` is `board` (the default), `updates` or `button`.
- `data-theme` is `auto` (the default), `light` or `dark`.
- `data-stage` and `data-type` set the board's initial filter.
- Values are passed through unchecked, but encoded (step 2); the embed's parsers ignore unknown ones.

**What the loader does.** Everything runs inside one IIFE, with no globals.

1. **Find itself.**
   - It reads `s = document.currentScript`.
   - With no script or no `data-game`, it calls `console.error` and stops: fail loud, but never break the host page.
   - It takes `origin = new URL(s.src).origin`.
2. **Inline widgets (board and updates).**
   - It creates an `<iframe>`: a title, `loading="lazy"`, `width: 100%`, `border: 0`, and a height of 400px until the first resize message.
   - It inserts the iframe right after `s`.
   - It reads `getComputedStyle(iframe).fontFamily`. That is what `font-family: inherit` resolves to on the loader's own element.
   - Only then does it set `src` to `origin/g/<game>/embed/<widget>?<query>#font=<font>`:
     - `<game>` through `encodeURIComponent`;
     - `<query>` from `URLSearchParams`, holding `theme` and, when set, `stage` and `type`;
     - `<font>` through `encodeURIComponent`.
   - So a value holding `&`, `#` or `/` can't break the URL.
   - The font travels in the URL fragment, so it never reaches the server, a log or a cache key.
3. **The floating button.**
   - A fixed `<button type="button">Feedback</button>` in the bottom-right corner, with `font: inherit`.
   - Its colours are neutral, light or dark by `data-theme`; `auto` follows the visitor's setting through `matchMedia`.
   - A click creates, the first time, a `<dialog aria-label="Feedback">` holding a Close button and the board iframe at `height: min(80vh, 720px)`, then calls `showModal()`.
   - The native dialog traps focus, closes on Escape and returns focus to the button.
4. **Messages.** One `message` listener, which accepts a message only when all three hold: `e.source === iframe.contentWindow`, `e.origin === origin` and `e.data?.critwire === 1`.
   - `resize` sets the iframe's height to `ceil(height)`, clamped to 0–20000 px. It applies to inline iframes only.
   - `close` calls `dialog.close()`.
5. **What it never does:**
   - set or read cookies, or touch storage;
   - make network requests of its own;
   - read `document.title`, `location` or any other part of the DOM;
   - leave globals behind.

**Protocol v1** (`src/lib/embed/protocol.ts`, documented in `docs/embed.md`):

| From → to | Message | `postMessage` target |
|---|---|---|
| embed → loader | `{ critwire: 1, type: 'resize', height }`, on every size change of `.cw-embed` | `'*'`; it carries only a height |
| embed → loader | `{ critwire: 1, type: 'close' }`, on Escape | `'*'` |
| vote page → embed | `{ critwire: 1, type: 'vote', issueId, votes, voted }`, after a successful vote or withdrawal | the page's own origin, so only a critwire-origin opener receives it |

**Versioning:**
- `v1.js` and protocol 1 may only gain optional attributes and new message types.
- Anything incompatible becomes `/embed/v2.js`, and embed pages keep answering v1 for good.
- The file opens with a comment saying so.
- The 5 KB gzipped budget is enforced by a test (section 12).

#### 4. Voting from the embed

**The flow:**
1. **The vote link.** Each row's vote control is `<a href="<item page>?ref=embed" target="_blank">▲ 12</a>`.
   - Its click handler calls `window.open(href, 'critwire-vote', 'popup,width=480,height=640')`.
   - If that returns a window, the handler calls `preventDefault()` and keeps the reference.
   - If it returns `null` (the popup was blocked), the link's default action opens a new tab instead.
2. **The page that opens.** It's the existing item page, `/g/<game>/feedback/<slug>`, a first-party page, so the one `cw_vote_token` cookie applies.
   - If the player already voted on the portal, the page shows "Upvoted" and the count already includes them.
   - So each browser has one vote per item across the portal and every site that embeds it, with no new cookie.
3. **The vote.** The player clicks "Upvote" (`VoteButton`; its call to the route doesn't change). On success, `VoteButton` also calls `notifyOpener()`, which posts `{ critwire: 1, type: 'vote', issueId, votes, voted }` to `window.opener`, if there is one, with the target origin `location.origin`.
4. **The best-effort part.**
   - The embed accepts the message only from its own origin and only from the window it opened. It then shows the new count and "Voted" on that row.
   - This works whenever the opener survives: the popup was allowed, and the host page has no strict COOP of its own.
   - It applies only to that page view.
5. **After a reload,** the embed shows whatever copy the browser or the edge holds, at most 5 minutes old (section 7). A vote clears no cache.

**COOP.** The app sends `same-origin-allow-popups` on every route except feedback item pages, which send `unsafe-none` so the popup keeps its opener.
- Item pages hold nothing private: public text, plus the player's own vote state, which a cross-origin opener can't read.
- They have no message listener, and other sites still can't frame them.
- Every other page, the admin included, keeps `same-origin-allow-popups`.
- Without the exception, voting still works; only step 4 is lost.

**Why a third-party page can't cast a vote without a click on critwire's own interface:**
- **The embed can't vote.** It contains no `VoteButton` and never calls `/api/vote`. Inside a third-party frame the `SameSite=Lax` cookie isn't sent, so it couldn't vote as the player anyway.
- **The host page can't call the API.**
  - `/api/vote` takes only `application/json` (`route.ts:34`) and sends no CORS headers, so a cross-site JSON `fetch` fails its preflight.
  - Forms and `no-cors` requests get a 400 before the body is read.
  - The Lax cookie isn't sent on cross-site POSTs either.
- **The vote page can't be framed** (`frame-ancestors 'self'`), so it can't be overlaid or clickjacked. The only framable routes are the two widgets, and they hold no vote control, only links that open critwire's page.
- **An opener can't click for the player.** A page that opens the item page itself can navigate it, or post messages it never reads. It can't send trusted clicks into another origin's window, and `notifyOpener` posts only to critwire's own origin.

#### 5. Headers

`next.config.ts` `headers()` entries, in order. The last match wins for each header name.

```ts
{ source: '/:path*', headers: [
    { key: 'Content-Security-Policy', value: "frame-ancestors 'self'" },
    { key: 'Cross-Origin-Opener-Policy', value: 'same-origin-allow-popups' } ] },
// The two widgets: any site may frame them, and every cache in front keeps them 5 minutes at most in total.
{ source: '/g/:game/embed/:widget', headers: [
    { key: 'Content-Security-Policy', value: 'frame-ancestors *' },
    { key: 'Cache-Control', value: EMBED_CACHE_CONTROL } ] },
// Feedback item pages keep their opener, so the embed's vote popup can report back...
{ source: '/g/:game/feedback/:slug', headers: [{ key: 'Cross-Origin-Opener-Policy', value: 'unsafe-none' }] },
// ...but the form, which the entry above also matches, doesn't.
{ source: '/g/:game/feedback/new', headers: [{ key: 'Cross-Origin-Opener-Policy', value: 'same-origin-allow-popups' }] },
// The loader is a contract: cached for a day, at the edge and in browsers.
{ source: '/embed/v1.js', headers: [{ key: 'Cache-Control', value: LOADER_CACHE_CONTROL }] },
```

- **Next keeps these `Cache-Control` values.** When a response already has one, Next 16.2 doesn't replace it, on pages (`next/dist/server/send-payload.js:58-62`, whose comment says it's there for `next.config`) and on static files. Route handlers keep their own (`app-route.js:393-396`), as the badge relies on. E2E asserts the exact values (E7), so an upgrade that changes this fails the suite.
- `LOADER_CACHE_CONTROL` is `public, max-age=86400, s-maxage=86400`.
- **nginx:** delete the COOP line.
- **`tests/int/nginx-headers`:** COOP moves from the kept headers to the forbidden ones, covering both `add_header` and `proxy_hide_header Cross-Origin-Opener-Policy`. The new failure modes, N9 and N10, are written before the change.
- **`docs/deploy.md`, Security headers:** the app owns both framing and COOP.

#### 6. The JSON feeds

**Both feeds:**
- **Rendering.** Dynamic route handlers (`force-dynamic`), with no `revalidate` (section 7).
- **Missing games.** `getGameProject(slug)` returning null (an unknown, held or suspended game) gives `404 {"error":"Not found."}`.
- **Headers.** Every answer, 404s included, goes through `feedResponse`:
  - `Access-Control-Allow-Origin: *`;
  - never `Access-Control-Allow-Credentials`;
  - `Cache-Control: EMBED_CACHE_CONTROL`;
  - no cookies read.
- **Methods.** GET only, with no preflight handling. Simple GETs need none.

**`updates.json`** is JSON Feed 1.1, served as `application/feed+json; charset=utf-8`. It lists the 20 newest published updates, as RSS does:

```json
{ "version": "https://jsonfeed.org/version/1.1",
  "title": "<Game> — Updates", "home_page_url": "<site>/g/<slug>/updates",
  "feed_url": "<site>/g/<slug>/updates.json", "description": "The latest updates for <Game>.", "language": "en",
  "items": [{ "id": "42", "url": "<site>/g/<slug>/updates/<slug>", "title": "v1.4 — Harbor hotfix",
              "summary": "…", "content_text": "<the summary, or the title>", "date_published": "2026-…Z" }] }
```

- `id` is the update's database ID, so it survives a slug change.
- `summary` is left out when empty.

**`feedback.json`** is contract v1, served as `application/json; charset=utf-8`:

```json
{ "version": 1, "title": "<Game> feedback", "home_page_url": "<site>/g/<slug>/feedback",
  "feed_url": "<site>/g/<slug>/feedback.json",
  "items": [{ "id": "123", "url": "<site>/g/<slug>/feedback/<slug>", "title": "…", "summary": null,
              "type": "bug", "stage": "under-review", "votes": 12, "date_created": "2026-…Z",
              "shipped_in": { "version": "v1.4", "title": "…", "url": "<site>/g/<slug>/updates/<slug>" } }] }
```

- **Values:**
  - `type` is `bug` or `idea`.
  - `stage` is `under-review`, `planned`, `in-progress` or `shipped`, from `publicStage()`. A null stage (an archived item reaching a public query) throws.
  - `shipped_in` is null, or a published update, from `shippedUpdate()`; its `version` may be null.
  - Every item has every key, with null when empty, so consumers never have to test whether a key is present.
- **Contents:**
  - `queryFeedbackFeed(projectID)`, new in `issues.ts`: `publicIssuesWhere`, `RANKED_SORT`, `SHIPPED_IN_SELECT` and `overrideAccess: false`, with the board's `select` plus `summary` and `createdAt`.
  - Only public, non-archived items, at most `FEEDBACK_FEED_LIMIT = 500`, pinned first, then by votes, then newest. `docs/embed.md` says the portal list has the rest.
  - Never `status`, the category, the studio's notes, report data or emails.
- **Stability:** fields may be added, but never removed, renamed or retyped. Anything incompatible gets a new URL (`feedback.v2.json`).

#### 7. Caching and freshness

- **No server cache.**
  - The two widgets and the two feeds render every request that reaches the origin. An edit, a hold, a suspension or a vote is in the next response.
  - Next's cache holds nothing for them, so made-up slugs don't grow it either.
- **One header, one bound.** `EMBED_CACHE_CONTROL = 'public, max-age=60, s-maxage=240'`:
  - a shared cache (Cloudflare, or any CDN) keeps a copy at most 240 s;
  - a browser keeps what it received at most 60 s more;
  - there's no `stale-while-revalidate`, so no layer serves a copy past its TTL;
  - so every viewer sees a version at most 5 minutes old, for edits, holds, suspensions and votes alike.
  - Both widgets and both feeds send it, their empty and 404 answers included.
- **The hooks** don't change. Edits keep refreshing the hub and the updates pages as they do today.
  - The Brief asks them to refresh the embeds and feeds too. There's no copy at the origin to refresh, and they can't reach Cloudflare without a purge token.
  - So an edit reaches studios' sites within the same 5 minutes as a vote (candidate handoff item 3).
- **A vote** clears no cache. The voter's own embed shows it at once through the popup message (section 4); everyone else sees it within 5 minutes.
- **Held or suspended.** The next origin response is an empty embed, which posts `height: 0` so the iframe collapses, and a 404 from both feeds. Copies already cached expire within 5 minutes.
- **Edge (`docs/deploy.md`).** One Cloudflare Cache Rule:
  - it matches `starts_with(http.request.uri.path, "/g/") and (http.request.uri.path contains "/embed/" or http.request.uri.path.extension eq "json")`;
  - it's eligible for cache, with Edge TTL "Use cache-control header if present, bypass cache if not", and Browser TTL "Respect origin";
  - it keeps the default cache key, query string included.
  - The app's header is the only source of TTLs, as it is for framing.
  - The rule must stay this narrow: the hub sends Next's `s-maxage=3600`, which the edge must not honour (`docs/deploy.md`, step 8).
  - Smart Tiered Cache, a free toggle, is optional: one data centre then fetches for all the others.
  - Cloudflare's defaults already cache the loader (a `.js` file), with its own header.
  - After a deploy, the doc's check: `curl -sI` an embed twice shows `cf-cache-status: HIT` and the header as sent, and `curl -sI` the hub shows `DYNAMIC`.
- **Cache keys and variants.**
  - Next's `_rsc` parameter keeps RSC payloads apart from HTML only while the query string is in the key (Next's CDN guide), so the key keeps it.
  - The embed makes no RSC requests anyway: no `next/link`, no router calls and no URL state.
  - The loader adds only the snippet's own `theme`, `stage` and `type`, so one snippet is one URL. The font is in the fragment, which never reaches a cache.
  - Made-up query strings miss the edge and render at the origin, as any dynamic portal page already does.
- **Origin cost.**
  - Behind Cloudflare, each URL renders at most once per 4 minutes per data centre.
  - Without a shared cache (a self-hosted instance), every view whose browser copy has expired renders: 15 small indexed queries for the board, about five for updates.
  - It's the badge's model. `docs/self-hosting.md` suggests a CDN for busy sites.
- **What E2E checks.** E2E runs `next start`, without Cloudflare.
  - It asserts the exact header on all four routes, their empty and 404 answers included, and that it has no `stale-while-revalidate` (E7).
  - It checks that an edit, a hold and a suspension show in the next response (E9, E10).
  - The edge's part rests on that header and on the deploy doc's `curl` check (candidate handoff item 2). A caching proxy written for the tests would only test itself.

### Rejected alternatives

- **Embed pages inside the portal tree, with the portal moved into a `(portal)` group.** It moves every portal file, changes `UPDATES_ROUTE`, and still inherits the preloaded body font from `(public)/layout.tsx`.
- **ISR (`revalidate = 300`) refreshed by the hooks, behind the edge.** Next serves an entry past its window once more, even after `revalidatePath`, and a route handler always does (Finding 1). The edge then keeps that response for its TTL, so a hold could show long after it. No honest bound without purge.
- **Purging Cloudflare from the hooks.** It needs an API token, a network call in every edit hook, and every query-string variant of every URL. The 5-minute bound holds without it.
- **A Cache Rule that overrides the origin ("Ignore cache-control header and use this TTL").** That's a second source of truth that E2E can't see. With "use cache-control header", the app's header holds behind any shared cache, and E2E asserts it.
- **Ignoring the query string in the edge cache key.** Next's `_rsc` parameter must stay in the key, or an RSC payload could be cached as the page. The variants are one per snippet.
- **One query of 500 items, filtered in the browser.** Past 500 items, stages look empty and counts are wrong, and it ships every item to every host page view.
- **Filters resolved on the server per click** (links, or nuqs with `shallow: false`). Each click becomes a round trip, an RSC request and an edge variant, and plain links add entries to the host page's history. All 15 views fit in a few KB.
- **The font in the query string.** It would reach the server, its logs and the cache key.
- **A `data-font` attribute instead of the inherited font.** The studio would have to type it, and the Brief asks for inheritance.
- **Sending the font by `postMessage` after load.** The fallback font would flash, and the widget would resize a second time.
- **A dedicated vote page for the popup.** It's a second URL for the same item, for a COOP exception that's just as safe on the item page.
- **Keeping COOP on item pages too.** Voting works, but "Voted" and the new count could never reach the embed. No channel survives the switch of browsing context group, because storage and `BroadcastChannel` are partitioned by top-level site.
- **Polling the vote count, or a nonce channel through the server.** New endpoints and requests for a best-effort label.
- **The loader adding `ref=embed` to the iframe URL.** The page doesn't read it, and it would add an edge variant. The embed tags its own links instead, which also covers the bare iframe.
- **A route handler for `/embed/v1.js`.** More code for headers that `headers()` already sets on a static file.
- **`localhost:<other port>` or `page.route` as the E2E host.** The first is same-site, so the Lax cookie would reach the frame. Chromium's private-network check blocks the second.
- **A caching proxy in the E2E suite.** It would test itself, not Cloudflare. The contract is the origin's header, which E2E asserts.

### Risks and conservative choices

- **The COOP exception on item pages is the one security-header change.**
  - It's scoped to item pages, which hold nothing private and can't be framed. Every other page keeps `same-origin-allow-popups`.
  - Reverting it means deleting two `headers()` entries; the embed then shows new counts only after the cache window.
- **The font is the one thing the loader reads:** the inherited `font-family` of its own iframe. If the owner reads "never read the host page" more strictly, delete that one line and the widget falls back to `system-ui`.
- **Host web fonts don't reach the iframe.** Only system font stacks match exactly. Documented.
- **Sandboxed host frames without `allow-popups`,** which some site builders use, can't open the vote popup or the portal links. Documented per platform; untried platforms say "should work".
- **Edits wait for the caches, like votes.** Every copy is at most 5 minutes old, and the hooks can't shorten that at the edge. Showing edits at once would need Cloudflare purge and an API token (candidate handoff item 3).
- **Next keeping our `Cache-Control` on pages** is what Next 16.2 does (`send-payload.js:58-62`), though older Next docs say `next.config` can't set it there. E7 asserts the exact header, so an upgrade that changes it fails loudly.
- **Origin load without a shared cache** (self-hosted instances): each view whose browser copy has expired runs the board's 15 queries. It's the badge's model. Documented, with a CDN suggested for busy sites.
- **Made-up query strings** miss the edge and render at the origin, as any dynamic portal page does today.
- **`prebuild` runs vitest inside the Docker builder,** where devDependencies are installed. It can't be checked on this VPS, which has no Docker. The test file runs in Node only.
- **Cloudflare's own cookies** (`__cf_bm`, under Bot Fight Mode) would appear in embeds. The app sets none. Documented.
- **Double-click tricks,** where a page opens the popup under the player's cursor, still need the player's real click on critwire's page. The prize is one vote per browser, as it already is.

**Handoff items.** Filed after the revision as H11 (item 1), H13 (item 2) and H12 (item 3) in `/srv/critter-ai/handoff/critwire.md`.

1. **Decision, with a default:** the item page doesn't send COOP `same-origin-allow-popups`, so the embed can show "Voted" and the new count straight away. The alternative is COOP on every page, with the embed's count updating within 5 minutes. Default: keep the exception, which can be reverted by deleting two `headers()` entries.
2. **Before the production deploy (it blocks nothing now):**
   - add the Cloudflare Cache Rule from `docs/deploy.md` on the production zone, and optionally turn on Smart Tiered Cache;
   - run the doc's `curl` check: an embed answers `cf-cache-status: HIT` on its second request, and the hub stays `DYNAMIC`;
   - check that Bot Fight Mode's `__cf_bm` cookie isn't set on `/g/*/embed/*`.
3. **Decision, with a default:** the embeds and feeds keep no server cache, so the hooks don't refresh them (the Brief asked that they would). An edit reaches studios' sites within 5 minutes, like a vote. Showing edits there at once would need Cloudflare purge, with an API token for the zone. Default: no purge.

## Architecture review (Astra)

MUST-FIX:

## Failure modes

Section 12 tests two parts in isolation: the loader's budget and APIs (`embed-loader`, S3), and nginx's headers (`nginx-headers`, S7). Their lists below are those tests' specification. They go into the tests before the code changes.

The other lists are the ways this mission's risky parts can fail. Each item names the E2E assertion that catches it. That assertion is written before the code, in the step shown.

**`embed-loader` (int, S3).** One checker runs over inline fixtures, one for each mode, and over the committed `public/embed/v1.js`.
- L1. A missing file fails, and the failure names its path.
- L2. An empty or whitespace-only file fails, so the check never passes vacuously.
- L3. A source whose gzip, at zlib's default level, is 5,120 bytes or more fails. The failure names its gzipped size and the budget.
- L4. The budget applies to the gzipped size, not the raw size: 20 KB of repeated text passes the size check.
- L5. Each forbidden API fails and is named, with one fixture per name: `document.cookie`, `localStorage`, `sessionStorage`, `indexedDB`, `fetch(`, `XMLHttpRequest`, `sendBeacon`, `document.title` and `.innerHTML`.
- L6. A forbidden name in a comment or a string fails too.
  - The check reads the source as text and never parses it, so it errs on the strict side.
  - It's a tripwire against accidents. E3, E5 and E6 check what the loader actually does.
- L7. Every problem is reported at once: an over-budget source that uses two forbidden APIs gives three problems.
- Outside the test file, `prebuild` must run this test on its own and stop the build. S3 and Verification step 6 pad the loader and watch `pnpm build` fail.

**`nginx-headers` (int, S7).** COOP leaves the kept headers, which become four.
- N9. `add_header Cross-Origin-Opener-Policy …` fails, at server level or in a `location`, in any letter case. The failure says that the app owns COOP.
- N10. `proxy_hide_header Cross-Origin-Opener-Policy` fails, in any letter case. It would strip the app's COOP, including the item pages' `unsafe-none`.
- N7 gains a COOP line that appears only in a comment. That line passes.

**The loader on a host page (S3, S5, S6).**
- R1. The frame can grow but never shrink, because the embed document keeps a `min-height` from `globals.css` or from the portal. E1.1 catches this when the frame shrinks after a filter change.
- R2. The loader acts on a message that didn't come from its own iframe, so a script on the host page can resize the frame. E1.2 posts a forged `resize` from the host page, and nothing changes.
- R3. An attribute value holding `&`, `#` or `/` breaks the iframe URL. E1.1 sets such a `data-stage`; it reaches the frame encoded, and the board shows All.
- R4. The font reaches the server, its logs or a cache key. E3 checks that the frame's request URL holds no font.
- R5. A crafted `#font=` value injects CSS, or an overlong one is accepted. E3 opens the embed with each, and the font stays `system-ui, sans-serif`.
- R6. A snippet without `data-game` throws and breaks the host page. E1.2 sees one console error and no iframe, and the host page's next script still runs.
- R7. Escape inside the frame doesn't close the dialog, or focus doesn't return to the button. E2 catches both.
- R8. The embed downloads a font file or an image, through a `next/font` import or CSS shared with the portal. E3 lists the frame's requests.

**Board data (S5).**
- W1. A count comes from the rows shown rather than from `totalDocs`, so a stage with 12 items reads 10. E1.1 compares the counts against REST and checks "See all 12".
- W2. The client payload carries `summary`. E1.1 searches the frame's HTML for every item's summary.
- W3. A filter click makes a request or changes a URL, which adds to the host page's history. E1.1 checks the frame's requests and the host page's `history.length`.
- W4. A game that takes bugs only shows the Ideas filter or "Suggest an idea". E1.1 seeds such a game, with `acceptIdeas: false`.
- W5. Links navigate inside the frame, or prefetch, as `next/link` does. E1.1 and E1.2 click a link and check three things: a new page opens, the frame stays where it was, and the frame requested no other portal page.

**Voting (S7, S8).**
- V1. One click opens both the popup and the fallback tab, or nothing opens when `window.open` returns `null`. E4 counts the new pages in both cases.
- V2. The popup loses its opener, because the item page sends `same-origin-allow-popups`, so "Voted" never arrives. E4's "Voted" check and E7's COOP values catch it.
- V3. The embed trusts a vote message from another window. In E4, the host page posts a forged one into the frame, and no row changes.
- V4. `notifyOpener` posts to `'*'`, which tells any page that opened the item page how the player voted. In E5, a host page opens the item page itself and the player clicks Upvote there; the host page receives nothing.
- V5. A vote through the embed counts twice, or sets a second cookie. E4's REST counts and E6 catch it.
- V6. The embed calls `/api/vote` itself. E5 watches the frame's requests.

**Feeds and caching (S4–S6).**
- C1. A field the portal doesn't show reaches a feed: the status, the category, the studio's notes, report data or an email. E8 checks exact key sets and searches both bodies.
- C2. A private, archived, draft or held item, or a draft or held update, appears in a feed. E8 catches it.
- C3. An empty value is left out instead of being `null`. E8 includes an item with no summary and no update.
- C4. A 404 has no CORS header, or any answer sends `Access-Control-Allow-Credentials`. E8 and E9 catch it.
- K1. Next rewrites our `Cache-Control`: `no-store` on a dynamic page, or an added `stale-while-revalidate`. E7 asserts the exact values on all four routes, empty and 404 answers included.
- K2. Next caches an embed or a feed, through a `revalidate` export or a static render. An edit, a hold or a suspension then misses the next response. E9 and E10 catch it.
- K3. A held game's embed doesn't post `height: 0`, which leaves an empty 400 px box on the studio's site. E9 catches it.
- K4. A held game's embed shows text or a theme. E9 checks that the frame has no text.

## Decisions

- **2026-10-02 · No server cache for the embeds and JSON feeds; the hooks don't refresh them (Brief Goal 6 deviation).** They render per request and send `public, max-age=60, s-maxage=240`, so edits, votes, holds and suspensions reach studios' sites within 5 minutes end to end, with no Cloudflare purge and no API token. ISR behind the edge had no honest bound (an expired entry is served once more after `revalidatePath`). Filed as H12 with this as the default.
- **2026-10-02 · The public item page drops COOP `same-origin-allow-popups`** so the vote popup keeps its opener and the embed can show "Voted" at once. Filed as H11 with this as the default.
- **2026-10-02 · Hook queries run in the write's transaction (found in S7).** `validateUniqueSlugPerProject`, `resolveProjectSlug`, `revalidateGameLanding` and `revalidateUpdatePage` queried without `req`, so each needed a second pool connection while its write held a transaction open. With 20 or more concurrent writes (the pool's `max`) every connection held a transaction and waited for another: the server deadlocked until restart. That was the `issues-voting` S4.2 hang logged in S5 (25 parallel creates; `pg_stat_activity` showed 19 connections `idle in transaction` after `begin`). They now take `req` and pass it. A pre-existing bug, outside the brief's scope, fixed here because S7's full suite can't pass without it and production would hang the same way.
- **2026-10-02 · E2E studio slugs pass the content filter (found in S7).** `seedStudio` named studios and games after `label-<8 random hex>`, and hex like `45545c47` reads as leetspeak ("455"), so the filter held the games and `limits` S12.2's submission got a 404. `cleanSlug` re-rolls until the app's own `screenText` passes it. Test-only.
