# Mission: critwire.com becomes Critter Connect's site

This file is the mission's state. Agents: follow "In a mission session" in `~/.claude/CLAUDE.md`, and keep this file current.

## Brief


### Goal

critwire.com serves one game, Critter Connect, as its public feedback and updates site, in the game's own **cc** look, light and dark.

1. **critwire.com is Critter Connect's site.**
   - `/` opens Critter Connect's hub (`/g/critter-connect`). Critwire's marketing home is no longer reachable. Every existing `/g/critter-connect/...` URL keeps working.
   - Every public page shows Critter Connect's brand: the game's logo and favicon, its name in page titles, and a Critter Connect default OG image. "critwire" remains only in the domain, the code and the repo.
   - "Powered by Critwire" is off on the live site through `CRITWIRE_HIDE_POWERED_BY=1`. `src/lib/hosting.ts` allows that while open signup is off. The deploy steps set it; the mission doesn't touch the live `.env`.
   - The multi-studio machinery stays in the code, dormant: tenants, signup, onboarding, hosted limits, the share kit and Discord. Only pages nobody can reach any more may be removed, together with their tests and CSS.
2. **The look is the game's cc theme, in place of cw, in light and dark.**
   - **Guidance:** cc's `GUI.md` and `gui/` replace cw's. `gui/themes/cw*.md` go, and `gui/themes/cc*.md` come in. The three skills and the other `gui/*.md` files are already byte-identical to cc's, so they stay. `GUI.md` gains a "Local decisions" section.
   - **Tokens:** cc replaces cw in the token layer that the cw-theme mission built, so every surface takes cc, dormant ones included. No cw value is left.
   - **Fully converted, in both modes, with before and after screenshots:**
     - The Critter Connect hub and all its pages: updates, the feedback list and board, item pages, the new-feedback form, contact.
     - The board, updates and floating-button embeds.
     - `legal/*`, `report-abuse` and the 404s.
     - The admin sign-in, forgot and reset views, and the custom admin views: dashboard, Issues kanban, Share tab, legal gate.
     - Payload's own UI, through its theme variables.
     - The share kit's images and badge.
     - The auth and contact-form emails.
   - **Modes:** the hub follows the visitor's system setting with cc light and cc dark, as the game does. Today a portal has one saved palette, dark by default. The architect picks the smallest change that gives Critter Connect's hub both modes, and other games' saved themes keep working.
   - **Status and audit:** every component in scope has a status, with evidence or a reason: converted, already matches, intentionally preserved, or blocked. A `graphical-audit` pass has found and fixed the remaining gaps.
3. **Real content in place of the demo.**
   - An idempotent one-off command turns the live data into the real site. It has a dry run that prints what it would change. It does this:
     - Renames the studio "Critwire Demo" to "Haunted Pavement".
     - Sets the game's name, one-line description and links from critterconnect.org and play.critterconnect.org.
     - Deletes the sample feedback items, the sample submission and the sample update.
     - Leaves a short draft first update ("the feedback board is open") for Danby to edit and publish.
   - It's proven against a copy of today's live state in the mission's own database; the seed reproduces that state. It's **not** run on `critwire_live`.
   - `src/seed/critterConnect.ts`, which the demo and the screenshots use, takes the same studio name, game details and cc look. It keeps sample content for previews.
4. **The legal drafts describe this site.**
   - `legal/terms.md` and `legal/privacy.md`, and `legal/copyright.md` where it needs it, describe Critter Connect's feedback and updates site, operated by **Haunted Pavement LLC**, for players who have no accounts. A short section covers the site's admin accounts, so the existing acceptance gate stays correct.
   - They're written from a fresh inventory of what the site collects from players today, taken from the code and the live `.env`'s variable names (never their values). It covers at least:
     - feedback text
     - the vote cookie
     - the contact form's email, kept until delivery
     - IP addresses for rate limits
     - Turnstile and Resend
     - server logs
     - anything else the inventory finds
   - **Players may be under 13** (Critter Connect is for grades 6–12). The drafts say so plainly. The Summary lists every question for Danby's lawyer about COPPA (the US children's privacy law), each with where in the code a child's data is touched. The mission doesn't answer legal questions itself.
   - The player forms' sensitive-information warning uses plain words for grades 6–12: don't put your real name, email, school or where you live in feedback.
   - The documents stay `draft`, and every `[placeholder]` stays for Danby. Versions follow the rules in `src/lib/legal/documents.ts`.
   - **The handoff:** H16 is rewritten to match the new drafts, with the placeholders and the COPPA questions. H8, H17 and H19 each get a note on whether they still apply, for Danby to decide.
5. **The in-game button is ready for Danby.** A handoff item gives the exact snippet for the floating Feedback button on play.critterconnect.org, and a link or embed for critterconnect.org. Both are tested on a local test page. Changing those sites is Danby's job.

### Why

On 2026-10-07 Danby decided that critwire won't compete with BetaHub as a product. Instead it becomes Critter Connect's own public feedback and updates site, and it should look like the game, so players feel they're in one place. The players are students in grades 6–12, so the site collects as little about them as it can and says so plainly.

- **Accessibility wins over snapshot values** (Danby's standing rule since cw-theme). Hold WCAG AA: 4.5:1 for text, and 3:1 for large text, field boundaries and focus indicators. Fix a failure with another cc token, never a new colour, and list it with its ratio. These failures are already known, measured on cc's own values:
  - **Button labels on `color-1` `#00906c`:** cc's `--cte-accent-text` gives 3.90:1 in light mode (`#fcfbfa`) and 4.06:1 in dark (`#241f16`). Black (`neutral-10` in light, `neutral-1` in dark, both `#000000`) on `color-1` gives 5.21:1.
  - **`color-1` as text:** 3.90:1 on the light surface and 4.06:1 on the dark surface (5.21:1 on the dark canvas). Don't use it for normal-size text in light mode, or on the dark surface.
  - **Light muted text:** `--cte-text-muted` `#837e72` on `#fcfbfa` is 3.91:1. Use a darker neutral, such as `neutral-8` `#595449`.
  - **Status colours as text:** in light mode, `success` `#00c853` is 2.16:1, `warning` `#ffea00` is 1.19:1 and `error` `#fc032d` is 3.91:1. In dark mode, `error` on the surface is 4.05:1. Use them as fills and marks with black text, always with an icon or a word.
  - **Edges:** cc's borders are 0 px with a colour at 20% opacity, which is close to invisible. Fields and controls still need a 3:1 boundary:
    - Light mode: `neutral-7` `#837e72` or darker on white. `neutral-6` is only 2.61:1.
    - Dark mode: `neutral-6` `#888377` on black (5.56:1). `neutral-5` is only 2.88:1.
  - cc is flat by design. The 0-opacity shadows are intended; don't "fix" them.
- **Fonts follow the game.**
  - Nunito stands in for the paid GT Maru, in the ui, brand and editorial roles. Open Runde takes the data role. Both are OFL. Self-host them from `source/fonts/` with their licences, and make no third-party requests.
  - Keep them behind the font-role tokens, so a licensed GT Maru can replace Nunito in one place.
  - If the share-image renderer needs TTF files, get Nunito's from its official OFL source, with the licence.
  - Remove a font that's no longer used only after checking that nothing uses it.
- **Icons.** cc names the paid "Central" set. Keep `lucide-react` at cc's stroke width of 2, and don't add an icon package.

**Problems, ranked.**

1. **High (bug the conversion would cause). cc's border steps are 0 px**, and the app uses `var(--border-s|m|l)` 63 times as *stroke widths*: control and field edges (`portal.css` `--fs-control-edge`), dividers, the status marks' rings (`globals.css` `.status-mark`), the selected-tab bar, link underline thickness, the share kit, the admin views and Payload's `--btn-border`. Swapping values alone would erase every edge, every field boundary (breaking WCAG 1.4.11) and two of the four stage marks. *Fix:* critwire-owned stroke widths (§3.1, D7).
2. **High (accessibility/robustness). `light-dark()` has no fallback.** It needs Chrome 123 / Firefox 120 / Safari 17.5. The players are grades 6–12, often on school Chromebooks past their auto-update date or older iPads. Without support every colour token is invalid and controls lose their fills. cw accepted this for studios; for a children's site it's a real defect. *Fix:* light values first, `light-dark()` inside `@supports` (§3.1, D3).
3. **High. No single "site" identity.** "Critwire" is hard-coded in ~15 user-facing places (table above), and the demo slug lives in a marketing module (`components/marketing/links.ts:8`, read by `reservedSlug.ts` and the seed). *Fix:* one module, `src/lib/site.ts` (§6).
4. **Medium (DRY). Duplicated metadata and palette wiring.** The two root layouts repeat the same `metadata` block; `embed.css` repeats the palette mapping three times ("Keep the two blocks equal"); `SENSITIVE_INFO_WARNING` and `_SHORT` say the same thing twice. *Fix:* one site-metadata module (§6), one palette mapping shared by portal and embed (§4), one warning sentence (§9).
5. **Medium (invented facts on a real site).** The seed's pitch, Steam link, platforms, version, contact domain and key art are made up, and the key art is a public file. *Fix:* the content command and the shared data module (§8).

### 2. Target design in one view

- **Sample identity: a record is deleted only if it is provably one of the seed's six samples (D40, D41, Astra MUST-FIX).** Why exact content can be the test: `/srv/apps/critwire` has only ever run `3054287` (its reflog is one clone and one reset), and `git diff 3054287 039ad28` changes none of Issues, PatchNotes, the content filter or their hooks, and IssueReports only by `submitterEmail`, whose column the deploy's migrations drop. So after the deploy's migrations, live's samples are field for field what `SAMPLE_CONTENT` holds. For each sample:
  - *Candidates* are every record in the game with the sample's key: the slug for the four items and the update (unique per game), the title for the report (not unique). None → already deleted, nothing to do. More than one → refuse as ambiguous, naming every ID.
  - *Content:* the candidate, read at `depth: 0` (with the transaction's `req` when applying), minus a fixed `VOLATILE` list, must deep-equal (`util.isDeepStrictEqual`, Node's own) `expectedSample(sample)` = the sample's `SAMPLE_CONTENT` fields (rich text as the stored Lexical JSON `lexicalFromText` writes) plus the collection's `SAMPLE_DEFAULTS` (items: not pinned, no needs-more-info or workaround text; the report: status `NEW`, no linked item, not flagged, empty Discord group; the update: `_status: 'published'`, not flagged). `VOLATILE` is `id`, `createdAt`, `updatedAt`, `publishedAt` (the seed's clock), `_order` (kanban position), `generateSlug` (Payload's slug bookkeeping) and `upvoteCount` (votes, counted separately), each with its reason in a comment. `tenant` and `gameProject` must be the studio's and the game's IDs; `fixedInPatchNote` must be the sample update's ID on `save-loses-clue-progress` and null on the other items. A key on one side and not the other is a difference, so a field added later can't pass unseen. The update is read twice, as published and with `draft: true` (its latest version), and both must match, so a saved but unpublished edit counts as an edit. `SAMPLE_DEFAULTS` is fixed against the live copy, where all six must match.
  - *Relations:* expected are the votes on a sample item (deleted with it, F22, and counted in the plan from `issue-votes`) and the sample item → sample update link. Anything else pointing at a sample refuses: a report linked to a sample item, a non-sample item shipped in the sample update, a `discord-posts` row. These are every foreign key into `issues`, `issue_reports` and `patch_notes` (checked in the migrations), apart from the update's own versions (`_patch_notes_v`, deleted with it) and Payload's document locks (`payload_locked_documents_rels`), which `overrideLock: false` covers below.

  - A refusal lists every problem found, not only the first, then exits 1 with nothing written.
- **Plan ID (D42).** The first 12 hex digits of the SHA-256 of the plan's change lines plus the `updatedAt` of the studio, the game and every sample. `--apply` refuses unless the plan it computes has the ID it was given, so what's applied is exactly what the operator read, down to the vote counts. One token binds the sample IDs, the game and studio changes and the counts.
- **`--apply <plan-id>`, in order (D43, D44):**
  1. Plan without a transaction; a refusal or a different ID stops here, with nothing written.
  2. Upload `public/brand/app-icon-512.png` to the studio's media unless it's there (`ensureMedia`, by filename and tenant). It runs before the transaction because a rollback can't remove a written file. The plan names the logo by filename, never by media ID, so the upload doesn't change the plan ID.
  3. In one transaction through `withTransaction(payload, fn)` (`src/lib/payload/withTransaction.ts`, the established helper: commit when `fn` resolves, roll back and rethrow when it throws):
     1. `lockSiteContent`: `SELECT … FOR UPDATE`, in this fixed order, on the game (by slug), its studio, and every candidate row (the items' and the update's sample slugs plus `FIRST_UPDATE.slug`, the report's title), each scoped by `tenant_id` and `game_project_id` (rule 2), through the transaction's own Drizzle handle (`payload.db.sessions[await req.transactionID].db`, the handle Payload's migrations get; a missing session throws) with `sql` from `@payloadcms/db-postgres`. Until commit, any edit or delete of those rows waits, and so does any insert that references them (a vote, a report linked to an item, a version of the update), because a foreign-key insert takes `FOR KEY SHARE` on the row it references, which `FOR UPDATE` blocks.
     2. Plan again with the transaction's `req` (READ COMMITTED: every read sees what was committed before the locks were granted); refuse unless the ID still matches.
     3. Write: the studio; the game (`gameChanges`: name, description, links, availability, contact, theme → `DEFAULT_THEME`, logo → the uploaded app icon, banner → none, since the demo art isn't the game's); delete the report, then the four items (`deleteIssueVotes` deletes their votes through the same `req`), then the update (an item points at it); create `FIRST_UPDATE` as a draft unless its slug exists. Every write passes `req`, `context: { disableRevalidate: true }` and `overrideLock: false`, so a sample, the game or the studio open in someone's admin makes Payload refuse and the transaction roll back.
  Nothing is session-scoped (no advisory or session locks, no `SET`), so it behaves the same behind PgBouncer in transaction mode, which pins one server connection for the length of a transaction; this VPS connects to Postgres directly.

A hook that ignored `disableRevalidate` would throw and roll back, loudly; the rehearsal would catch it.
