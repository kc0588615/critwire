Decide what makes a row the row it is, and let the database refuse what breaks the rules: primary, alternate and foreign keys, UNIQUE, CHECK and generated columns. The first part runs in this browser, on the tables the Schema page describes; the last part runs in your own PostgreSQL (the setup page).

Concept

An entity is a kind of thing a database keeps facts about, each one with its own identity: an animal, a country, a dataset, a record. Each entity becomes a table, and each table needs a key: a column, or a set of columns, whose value picks out exactly one row.

  • A table can have several candidate keys: columns, or sets of columns, that are never NULL and never repeated, so each one picks out every row. species has three: id, slug and scientific_name. The one picked as the main key is the primary key. The others are alternate keys, declared NOT NULL and UNIQUE. species also has six ids from other websites, declared UNIQUE too. Some animals have none of a given kind, so these are optional unique ids, not candidate keys: an id that is missing can't pick out its row.
  • A natural key is one the world already uses: a scientific name, a country's ISO code, GBIF's dataset key. A surrogate key is a number the database makes up and that means nothing else: critwire's species.id. Natural keys change (a species moves to another genus, a name turns out to be a synonym), and every row that points at one has to change with it; a surrogate never has to. critwire uses both: id (an integer, never reused) is the primary key, and the natural keys are UNIQUE. A natural key makes a good primary key when an authority keeps it stable and it is never missing: countries.code (ISO 3166-1) and datasets.dataset_key (GBIF's identifier) are primary keys here.
  • UNIQUE allows any number of NULLs, because one unknown value isn't equal to another: animals with no NCBI id don't collide. That is why an outside id can be an optional unique id, but not a candidate key, let alone the primary key.
  • A foreign key says a column's value must be a key of another table: occurrences.species_id REFERENCES species (id). It checks two things. A value that is inserted or changed must exist in the other table, or be NULL. And a row that other rows still point at can't be deleted or given another key, unless the foreign key says what to do instead (ON DELETE CASCADE deletes the children too, ON DELETE SET NULL empties their column). That is all it checks: not that the value is the right one, not rules that span rows, and with a key of two columns, a row with one of them NULL isn't checked at all (MATCH SIMPLE, the default). PostgreSQL also doesn't index the referencing column for you (Indexes and query plans, d3, in preparation).
  • A CHECK is a condition every row must meet, such as month BETWEEN 1 AND 12. It refuses a row only when the condition is false. When it is NULL (unknown, Select and filter, f1) the row passes, so a CHECK doesn't replace NOT NULL. A CHECK can compare columns of the same row: taxa's says a class has no parent and every other rank has one.
  • A generated column is computed from other columns of its row and can't be written directly. The lab's occurrences.geom is the point made from longitude and latitude, so the point and the two numbers can never disagree.
  • Foreign keys set the order of a load: a parent row goes in before its children (the browser setup inserts taxa one rank at a time, top down), and out after them.

Result

Every key refused what it should: a second animal with id 25 or with the tiger's GBIF id, a month of 13, a genus with no parent, an animal in a genus that doesn't exist, a genus that is a family once a two-column foreign key checked the rank, the deletion of a dataset its records still point at, a write to a generated column and the same field note twice. What got through is as instructive: a record with no month and no country (a CHECK and a foreign key both pass NULL), and a record that says Australia while its point is in Brazil (a foreign key checks that a value exists, not that it is true). occurrences' primary key is indexed and its three foreign keys aren't. critwire's design follows from this: a surrogate primary key, the natural keys NOT NULL and UNIQUE, the outside ids UNIQUE but optional (some are missing, and four names already changed in GBIF's eyes), and natural primary keys only where an authority keeps them stable (countries, datasets).

Dialects

  • PostgreSQL: as here, with surrogate keys from GENERATED ALWAYS AS IDENTITY (or the older serial); generated columns are STORED only (virtual ones come in PostgreSQL 18); foreign keys take ON DELETE CASCADE | SET NULL | RESTRICT, can be DEFERRABLE (checked at commit), and can be added NOT VALID and checked later with VALIDATE CONSTRAINT; UNIQUE NULLS NOT DISTINCT makes NULLs collide; no automatic index on a foreign key.
  • DuckDB (this page's browser engine): keys as here, but foreign keys only in CREATE TABLE, with no CASCADE or SET NULL actions; no identity columns (a CREATE SEQUENCE and DEFAULT nextval('…') do it); generated columns are virtual only; primary keys and UNIQUE build an index, which also makes bulk loads into keyed tables slower.
  • SQL Server: IDENTITY(1, 1) for surrogates; computed columns (AS (…), PERSISTED to store them); a UNIQUE constraint allows only one NULL (a filtered unique index, WHERE col IS NOT NULL, allows many); foreign keys take ON DELETE CASCADE | SET NULL, and NOCHECK turns one off, which leaves it untrusted until it is re-checked; CHECK passes unknown, as here.
