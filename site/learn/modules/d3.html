Find out why a query reads the whole table, and what makes it read only the rows it needs: B-tree, GiST and BRIN indexes, plans from EXPLAIN ANALYZE, and the statistics the planner chooses by. Everything runs in your own PostgreSQL, on the lab tables (the setup page).

Concept

PostgreSQL stores a table as 8 kB pages, about fifty records to a page in occurrences. A query that has nothing better reads every page, in order, and tests every row: a sequential scan. An index is a second structure, kept in step with the table, that leads from a value to the rows holding it. Before running a query, the planner writes several plans and picks the one it expects to read the fewest pages for the least work. That expectation comes from the statistics ANALYZE collects. So "why is this a sequential scan?" has four usual answers: there is no index that fits; the query hides the column inside an expression; the filter keeps so many rows that reading the whole table is cheaper; or the statistics are wrong.

  • A B-tree (the default, CREATE INDEX … ON t (col)) keeps the values sorted. It finds one value, a range (BETWEEN, >=) or rows in sorted order (ORDER BY … LIMIT). An index on (a, b) is sorted by a, then by b inside each a: it jumps straight to a = 48 AND b = 2010 or to a = 48, but a condition on b alone has nothing to jump to.
  • How the rows are fetched shows in the plan. An Index Scan walks the index and fetches each row as it goes, in index order. A Bitmap Index Scan first collects every matching row's location, then the Bitmap Heap Scan reads each page that holds one, once, in page order (Heap Blocks: exact=6 is six pages). Which the planner picks depends on how many rows match and how scattered they are: rows stored in roughly the index's order (a high correlation, below) favour the Index Scan. An Index Only Scan answers from the index alone, when every column the query needs is in the index and VACUUM has marked the pages all-visible. Because that depends on when autovacuum last ran, the labs below always ask for a column outside the index. That removes one source of variation, not all: a plan can still change with the PostgreSQL version or the statistics, so each lab says what its plan must show, not what its text must be.
  • Statistics live in pg_statistic, readable through the view pg_stats: per column, the share of NULLs, the number of distinct values, the most common values with their frequencies, a histogram of the rest, and the correlation between the values' order and the rows' physical order (1: stored in value order; 0: scattered). ANALYZE reads a sample of 300 × default_statistics_target rows (100, so 30,000), and autovacuum runs it again after enough of a table changes. After a bulk load, run it yourself: the lab file ends with ANALYZE on every table. The planner treats columns as independent, which goes wrong when one column predicts another; CREATE STATISTICS teaches it how they go together.
  • A GiST index on a geometry column stores each shape's bounding box in a tree of boxes. A spatial test like ST_Intersects, ST_Covers or ST_DWithin adds a box comparison the index can answer (&&, boxes overlap; @, box inside box), then runs the exact test only on the rows whose boxes passed. A test the index can't turn into a box, such as ST_Distance(…) < d, computes on every row. The lab file builds one on every geometry column (occurrences_geom_idx). Spatial indexes (g5, in preparation) goes further: nearest neighbours with <-> and geography.
  • A BRIN index keeps one summary, the smallest and largest value, per range of pages (128 by default). It is tiny, and it can only rule out ranges, so it helps as far as the values follow the physical order: most when they do (an id that grows as rows are appended, the time of a log line), partly when they roughly do (lab step 16 skips three ranges of seven), not at all when they are scattered. The column's correlation, from 1 or −1 down to 0, tells you how far.
  • EXPLAIN prints the chosen plan; EXPLAIN ANALYZE also runs the query and adds what really happened at each step (actual rows, Rows Removed by Filter). Read a plan from the innermost, most indented line outwards. On your own, use EXPLAIN (ANALYZE, BUFFERS), which adds the planner's estimated cost and rows, the time and the pages read. The labs print EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF), the plan's shape and its row counts only, because costs and times vary from machine to machine. Each lab lists what its plan must show: a text some line contains (Index Cond: (species_id = 63)), a text no line contains (no Seq Scan), and how many rows the top node returns. The plan printed under it is an example, from the versions named above the first block; yours may differ in its details and still be right. EXPLAIN ANALYZE on an INSERT, UPDATE or DELETE really changes the rows, so wrap it in BEGIN … ROLLBACK.
  • Indexes aren't free. Every index makes every write slower and takes disk space, and a primary key or UNIQUE constraint already brings one (Keys and constraints, d1). A foreign key doesn't: index its column when you join or delete through it. And a bulk load is faster when the indexes are built after the rows are in, which is why the lab file adds its keys and indexes after loading the data.

Each lab below starts from the loaded tables: critwire's tests run every block in a transaction and roll it back. To do the same in psql, type BEGIN; before a lab and ROLLBACK; after it, so the indexes you make in one lab don't change the plans of the next. The download runs the blocks in order, each after the blocks it needs.

Result

A filter on an unindexed column reads the whole table (40,386 of the pangolin's 40,395 rows thrown away); a B-tree turns it into six pages, and turns the slug join from a hash join over every record into a nested loop over nine. The planner skips an index when the filter keeps most of the table (72 % of records are from 2000 on), and can't use it when the column is inside an expression (year / 10); rewriting the filter as a range fixes that. A two-column index jumps on its first column; on its second alone, PostgreSQL 16 reads all of it. The planner's beliefs are in pg_stats: exact for one column after a full ANALYZE, but its independence assumption put the devil's Australian records at 230 when there are 1,998, until extended statistics recorded the pair. GiST answers ST_Covers and ST_DWithin through bounding boxes and leaves ST_Distance to a full scan. BRIN is three pages and helps as far as the rows are stored in the column's order: 512 pages read for the 1850s as loaded (partly ordered), 128 on the sorted copy.

Check

The answer: an index on the filter's equality column first, then the sort's columns in the sort's order. PostgreSQL reads a B-tree in either direction, so (species_id, year, id) serves year DESC, id DESC backwards; (species_id, year DESC, id DESC) is the same index read forwards.

Compare your plan with the answer's: a Limit over an Index Scan or Index Scan Backward on your index, the top node returning 20 rows, its Index Cond holding both the animal and the years, and no Sort or Seq Scan anywhere. Then run the query itself: its twenty rows equal d3-ex-rows'. An index on (species_id) alone, or on (year, species_id), still needs the Sort.

Dialects

  • PostgreSQL: B-tree, hash, GiST, SP-GiST, GIN and BRIN; partial indexes (… WHERE basis_of_record = 'PRESERVED_SPECIMEN'), expression indexes and INCLUDE columns for index-only scans; CREATE INDEX CONCURRENTLY builds without blocking writes (not inside a transaction); EXPLAIN (ANALYZE, BUFFERS), which PostgreSQL 18 prints by default; CREATE STATISTICS for columns that go together; skip scan from 18.
  • DuckDB (the browser engine of other modules): stores tables by column and keeps a min-max summary (a zonemap) of every column in every row group automatically, BRIN's idea built in, so it scans and skips rather than seeks. CREATE INDEX builds an ART index, used for primary keys, UNIQUE and very selective equality lookups only; the spatial extension adds an R-tree (USING RTREE); EXPLAIN ANALYZE prints the plan with timings.
  • SQL Server: a clustered index is the table, stored in key order (one per table); nonclustered indexes point to it (the plan's Key Lookup is PostgreSQL's fetch from the table), with INCLUDE columns and filtered indexes (WHERE …); columnstore indexes skip row groups by their min-max, as BRIN does; spatial indexes are grids, not trees; statistics are created and updated automatically, and SET STATISTICS IO ON with the actual execution plan shows the pages read.
