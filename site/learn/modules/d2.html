Decide which table each fact belongs in, so that every fact is stored once and the tables can't contradict themselves: functional dependencies, the normal forms from first to third, nested records turned into tables, and when repeating a fact on purpose is safe. Everything runs in this browser, on the tables the Schema page describes and on critwire's published file.

Concept

  • A functional dependency, written X → Y, says that a value of X fixes the value of Y: two rows with the same X always have the same Y. dataset_key → title: a dataset has one title. genus → family: every Panthera is a cat. The direction matters: two datasets can share a title, so title → dataset_key doesn't hold. A key is a set of columns every other column depends on.
  • A dependency is a rule about the world, which the designer states; it isn't read off the data. Rows can refute one (two rows, same X, different Y), never prove it: a rule that holds in today's rows may break with tomorrow's load. Once a table's key enforces the rule, the database refuses the row that would break it (Keys and constraints, d1).
  • A table that stores a fact in more than one place invites three anomalies. Update: a fact changed in some of its copies leaves the table saying two things. Delete: deleting the last row that held a fact deletes the fact (a record removed as a misidentification takes its dataset's only copy of the title with it). Insert: a fact can't be stored until something else exists (a dataset can't be listed before it has a record).
  • The normal forms remove them one kind at a time.
    • First normal form (1NF): one value per cell, no lists or repeated groups of columns. A list in a cell can still be queried: unnest turns it into rows, which can then be joined and counted (the worked example does). What the list loses is the database's checks on each item: no foreign key can say every country code in it is a countries row, no UNIQUE can stop a code appearing twice, and every query has to unnest it first.
    • Second (2NF): in a table whose key has several columns, no other column depends on only part of it.
    • Third (3NF): no column outside the keys depends on another column outside them. The short version of all three, "every column depends on the key, the whole key, and nothing but the key", is a first approximation. The exact rule: for every dependency X → Y in the table (with Y not part of X), either X contains a key, or Y is part of some candidate key. Boyce–Codd normal form drops the second escape: X must always contain a key. It differs from 3NF only in tables with several overlapping keys; critwire's tables don't have that case.
  • Normalizing splits a table along its dependencies. The split is lossless when joining the parts gives back exactly the rows you started with. A split into two parts is lossless when the columns they share determine all of one part, that is, they are a key of it: the flat table of lab step 3, split on dataset_key (the key of the datasets part), is lossless. Split on title instead, two datasets that share a title would each join to the other's records, and the join would add rows that were never there.
  • A nested file (JSON, or Parquet with structs and lists) groups facts by how they are read: one animal with everything about it. Tables group them by what they depend on. critwire keeps both: its build writes /v1/species.json and species.parquet nested, one record per animal, because that is how a reader wants them, and loads the same records into PostgreSQL tables whose keys and CHECKs refuse a record that breaks them, a check before anything is published.
  • Denormalizing is repeating facts on purpose, for reading: the published files, a star schema (Star schemas, d6), a summary table. It is safe when every copy is rebuilt from one source every time and never edited by hand. A value that is only a count of other rows (records per dataset) stays a query.

The record's sources is a list of structs: each item names a source, its license, when critwire retrieved it, and the fields it supplied. Does a source's license depend on the source? In the file, each source has one license, written once per animal it supplied:

So source → license goes into its own table, sources, one row per source, and SELECT DISTINCT over the file gives exactly one row each. Its primary key now holds the rule: had two animals' entries named two licenses for one source, the load would have failed instead of storing both. The file repeats each license 69 to 76 times, and that is fine, because critwire's build writes the file from one source every time, and gives every animal's entry for a source that source's one license. Which source gave which field is a fact about the animal and the field together, so it goes in species_sources, keyed (species_id, field). Lab

Is a license a fact about a record or about its dataset? GBIF gives both: every dataset declares a license, and every record carries one. If dataset_key → license held, the license would belong in datasets (3NF), stored 400 times instead of 40,395.

  1. Test the rule on the records: does any dataset have records under two licenses?

    {{block:d2-fd-license}}

    None, in this sample. That doesn't prove the rule (Concept). The full GBIF download the sample comes from refutes it: the iNaturalist research-grade dataset holds 9,581 CC BY records and 3,152 CC0 records. The sample just doesn't show it, because iNaturalist declares CC BY-NC for the dataset, so none of its records passed the sample's license rule (the lab data page).

  2. Is the record's license the dataset's declared one?

    {{block:d2-license-differs}}

    Not always: this museum declares CC0 for its dataset and CC BY for these records. So there are two facts here, under one word. The record's license depends on the record and stays on occurrences; the dataset's declared license depends on the dataset and stays on datasets. Moving the first into datasets would publish these four records as CC0 and lose the credit their license asks for. (The sample's license is the stricter of the two.)

  3. Now the anomalies, on a flat table: each record with its animal's name and its dataset's title and publisher, the shape a spreadsheet export has. Every record carries its dataset's title, 400 datasets' titles stored 40,395 times. And there are fewer titles than datasets: two titles are shared, so a title can't stand in for a dataset key.

Result

The nested record became tables along its dependencies: the country list into rows (1NF), the country's name into countries (2NF), the family into taxa and the source's license into sources (3NF), with the published file repeating them for readers, rebuilt each time. The license question has a two-part answer. In the sample, no dataset has records under two licenses, but the full download has one (iNaturalist), and one museum's records carry a stricter license than its dataset declares. So the record's license is a fact about the record and stays on occurrences; datasets.license is the dataset's own declaration, a different fact. The flat table showed what normalizing prevents: 40,395 copies of 400 titles, one dataset with two titles after a partial fix, and 84 datasets lost with their last records (316 left of 400). And a record count per dataset is a query, not a column: stored, it would be wrong after the next load.

Dialects

  • PostgreSQL: nested data is jsonb (or arrays and composite types); jsonb_array_elements, jsonb_to_recordset and unnest(array) turn it into rows, -> and ->> reach into it, and jsonb_agg and jsonb_build_object build it back for a published file.
  • DuckDB (this page's browser engine): STRUCT, LIST and MAP columns, read from Parquet or JSON (read_json); unnest and dot access as here, to_json and list(…) to nest again.
  • SQL Server: no list or struct types: JSON is text (SQL Server 2025 adds a json type), shredded with OPENJSON(…) WITH (…) under CROSS APPLY and built with FOR JSON PATH; STRING_SPLIT splits a delimited cell.
